## Product summary

Haystack is a personal bookmarking service for tools, GitHub repositories, articles, and similar resources. It is built for a single user first, and it should stay ready to open to the public later without a rewrite.

A browser extension captures the current page and opens a prefilled save form on the Haystack site, in the style of a social share button. The user confirms the save there. The service enriches each bookmark with structured metadata produced by a large language model, and classifies it with Jev. The web interface is a single search field. The user describes what they are looking for in natural language, typed or spoken. Jev judges how well each bookmark serves the query, and the results are shown as cards containing the title and description. Each card links to the resource.

## Goals and non-goals for v1

The product is delivered in four milestones, described under "Milestones and phases": capture, enrichment, search, then agent access through MCP and WebMCP. Milestones 1 to 3 make up v1. Milestone 4 is planned from day one, and the design keeps it cheap to add, but it is scheduled after v1. Each milestone is deployed to production before the next one starts, so real bookmarks accumulate from the end of Milestone 1 onward.

By the end of Milestone 3, v1 must do the following. It must save a bookmark from the extension with one click to open the save form and one click to confirm. It must enrich that bookmark asynchronously with metadata designed for Jev matching. It must return ranked results for natural-language queries. It must log every search in enough detail to evaluate thresholds and question designs offline. It must run within Cloudflare's free tier, which Q1 chose over Workers Paid.

The following are explicitly out of scope for v1: open sign-up for anyone with a Google account, candidate shortlisting with embeddings, bookmark editing after saving, tagging, folders, sharing, and import from other services. Shortlisting is deferred until collection size makes it necessary.

## Decisions made

These decisions came out of the planning conversation and should not be reopened without discussion.

1. **Platform.** Cloudflare Workers hosts the whole site from a single Worker. D1 provides persistence. Every HTML page is rendered or gated by the Worker behind Google sign-in. Only CSS, JavaScript, fonts, and images are served as static assets.
2. **Metadata capture happens in the extension, and saving happens on the site.** The extension reads the rendered page's title, meta description, and Open Graph tags, then opens `/save` with those values as query parameters. It holds no credentials and makes no API calls. The server fetches a page in one case only: when a signed-in user submits the site's address form, which posts the address to `POST /save/address`, and only after the address has passed the same checks as `GET /save`. It then reads the page's head for the same values as the extension, within a 3-second time limit and a 256 KiB byte limit, and redirects to the save form with them. It fetches nothing for the extension, for any `GET`, or for any other route. The fetch is behind a POST because opening a link can have side effects, such as using up a magic sign-in link. See "Looking the page up (#105)" under "Save flow". _Amended 2026-10-19 (#105): this decision said that the server does not fetch arbitrary pages in v1._ The Open Graph values and the plain values are sent as separate fields, and the enrichment model weighs them. We do not decide up front which source to trust, because both are often shaped for search engines.
3. **GitHub is special-cased.** For `github.com/{owner}/{repo}` URLs, the server calls the GitHub REST API for the description, topics, primary language, and an excerpt from the README.
4. **Enrichment uses a pluggable LLM provider.** A provider interface with adapters for Anthropic, OpenAI, Cloudflare AI Gateway, and OpenRouter. Every provider's output is validated against a Valibot schema at the boundary, regardless of which provider produced it.
5. **Jev is called directly** through the TypeSafe HTTP API with a TypeSafe API key. It is not called through the Workers AI binding.
6. **Jev handles the typed judgments at ingestion.** The `kind` classification is a Jev Choice question, so the LLM only generates prose fields.
7. **Search asks both Noul and Score.** Each query-bookmark pair gets a Noul question and a Score question in the same request. We do not choose between them in v1. Both answers are logged and compared on real data.
8. **Evidence goes in state.** The query and the bookmark are placed in the Jev `state`. The judgment goes in `instructions`, and the possible answers go in `criteria`. Bookmark content never goes in the criteria.
9. **Google sign-in from day one, on the site only.** The site signs users in with Google (OpenID Connect). Because the extension only opens pages, the site session is the single authentication mechanism. `user_id` always comes from the session, never from the client. v1 restricts sign-in to an allowlist of email addresses, so real multi-user support exists without opening the service to strangers who would spend the LLM and Jev budget.
10. **Voice input in v1 uses the browser's Web Speech recognition only.** Voice is progressive enhancement layered on the text input, which always works. Web Speech needs no server code, and Schalk searches mostly in Chrome. Whisper transcription on Workers AI is in the backlog for browsers without Web Speech, such as Firefox. (Revised 2026-10-06; this decision originally included both voice modes.)
11. **Secrets.** varlock and its 1Password plugin supply secrets for local development only. Deployed Workers use secrets set in Cloudflare, and CI needs none. Secret names are declared in `secrets.required` in `apps/worker/wrangler.jsonc`. (Narrowed 2026-10-10: deploys do not use varlock.)
12. **The share-style save flow.** `/save` serves the extension and the site's own address form, where a user types or pastes an address (#97). It is designed to serve other entry points later (a bookmarklet, and the Web Share Target API for an installed web app) without changes to the flow. Every way in ends at a `GET /save` link, so they all reach the same confirmation form and the same checks. The address form gets there through a redirect from `POST /save/address`, which first looks the page up (#105).
13. **No model routing.** Each provider adapter has its model chosen in configuration ahead of time. Jev does not route enrichment between models.
14. **Capture ships first.** Milestone 1 is deployed with saving only. Bookmarks saved before Milestone 2 have no enrichment, and that is exactly the set the first enrichment run processes.
15. **Enrichment runs as a permanent sweep.** One idempotent operation, "enrich every bookmark without an enrichment at the current schema version," handles the first backfill, later schema version changes, and retries after on-save failures. It stays running after the backfill because it is the retry mechanism. See "Enrichment sweep."
16. **Drizzle for the schema, queries, and migrations**, with `wrangler d1 migrations` as the only tool that applies migrations. See "Data model."
17. **Bookmarks are not editable after saving, but their owner can delete them.** The title and description are confirmed on the save form before submission, and that is the only chance to change them. Deletion is available from the recent saves list, the search results, and the review page at `/held`. See "Deleting bookmarks."
18. **URLs that carry secrets must never be saved.** Haystack tells users plainly not to save them, and refuses the patterns it can recognize, in the extension before the URL is sent and again on the server. From Milestone 2, Jev adds a probabilistic check on a redacted form of the URL: it warns on the save form, and it gates enrichment so that nothing unchecked is sent to a third party. Jev never sees the raw URL. See "Sensitive URLs."
19. **Agent access through MCP and WebMCP is part of the product, starting search-only.** Milestone 4 adds a WebMCP tool on the search page and a remote MCP server, both exposing only search. The remote server targets the stateless MCP specification (2026-07-28), so there are no protocol sessions to manage. To keep Milestone 4 cheap, search is built from Milestone 3 onward as one service, `searchBookmarks(userId, query, { channel, inputMode })`, that the web API, WebMCP, and MCP all call. `inputMode` is set only for the web channel, and it is passed so that the service can log it. See "Agent access."
20. **Runtime switches use Cloudflare Flagship.** Settings that must change without a deploy are Flagship flags, read through the Worker binding. These settings are listed under "Secrets and configuration." Static configuration stays in `vars`, and secrets stay secrets. Flagship is in public beta. See Q13. (Added 2026-10-06.)
21. **v1 starts on Wrangler and moves to the `cf` CLI later.** Cloudflare's `cf` CLI (beta since 2026-09-28) will replace Wrangler. Wrangler gets 18 months of maintenance after the `cf` beta ends. v1 uses Wrangler, because `cf` does not yet support three things this project needs: varlock for secrets, a command that sets a single secret (it only uploads secrets from a file on disk with `--secrets-file`), and a confirmed replacement for Wrangler's `createTestHarness`. Choices made now favor a later `cf migrate`, such as building through the Cloudflare Vite plugin (Q10 (b)). See Q14 for when to switch. Do not run `cf dev`, `cf build`, or `cf deploy` in this repository before `cf migrate`. The `cf` documentation warns that they can overwrite `package.json` and `vite.config.ts`, and Calavera manages both files. `cf` resource commands, such as `cf d1 list`, are safe to use alongside Wrangler. (Added 2026-10-06.)

## Open questions

These must be answered before the phase that depends on them starts.

**Q1. Default request mode and Workers plan.** Pair mode makes one Jev request per bookmark for every search. That collides with two limits. The first is Jev's rate limit of 1,200 requests per minute (see "Jev model limits" below): with 200 bookmarks, pair mode allows only six searches per minute. The second is the Workers subrequest limit per invocation, 50 on the free plan (see Q3). Workers Paid only solves the second. The working assumption is therefore that batched mode is the production default and pair mode is the reference used in evaluations. Phase 12 decides whether batching degrades quality enough to justify pair mode plus earlier shortlisting. Whether Workers Paid was wanted for other reasons, including the limits in Q3, was Schalk's decision, recorded below. Q3 records the free plan's CPU time limit per request, and Phase 11 checks `/api/search` against it. Search parses and validates a Jev response that grows with the collection, ranks the results, and writes one log row per candidate. All of this is CPU work, unlike the waiting on the network that enrichment does. At 10 ms, search will probably go over the CPU limit before the subrequest limit matters. The review recommended settling the plan question before Phase 7, not Phase 11, which #119 did. The project already pays for Jev and the LLM, and Workers Paid removes a group of limits that otherwise affect the design of the sweep, the chunker, and logging. _Blocks Phase 11._

_Decided 2026-10-22 (#119): Haystack stays on Workers Free._ Schalk chose Free over Workers Paid, which costs $5 a month. The limits that come with Free are recorded in Q3, and the sweep is sized to fit them. Time Travel therefore keeps its 7-day window (see "Backups and restore"). Revisit the decision if the CPU measurements in Phase 9 (#130 for the sweep, #133 for saves) show runs or saves going over the 10 ms limit, because Workers Paid is the one fix that needs no change to the design. The check of `/api/search` against the 10 ms limit stays with Phase 11, because no search code exists yet, so Q1 still blocks Phase 11 for that check.

**Q2. Resolved.** See "Jev model limits" below.

**Q3. Limits on background work.** The enrichment sweep runs on a Cron Trigger, and the on-save fast path uses `ctx.waitUntil`. Verify the current free-plan limits that apply to each: the number of Cron Triggers, CPU time per invocation (enrichment is mostly waiting on network calls, which should not count toward CPU time, but confirm this), and subrequests per invocation, which caps how many bookmarks one sweep tick can process. These numbers set the sweep's batch size. _Blocks Phase 8._

_Answered 2026-10-22 (#119)._ The limits come from Cloudflare's [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) page (last updated 2026-10-12, read on 2026-10-21 and 2026-10-22), and the cron details from [Cron Triggers](https://developers.cloudflare.com/workers/configuration/cron-triggers/), read on 2026-10-22.

| Limit                                               | Workers Free | Workers Paid                                                   |
| --------------------------------------------------- | ------------ | -------------------------------------------------------------- |
| CPU time per HTTP request                           | 10 ms        | 30 seconds by default, up to 5 minutes                         |
| CPU time per Cron Trigger run                       | 10 ms        | 30 seconds for an interval under an hour, 15 minutes otherwise |
| Wall time per Cron Trigger run                      | 15 minutes   | 15 minutes                                                     |
| How long `ctx.waitUntil` may run after the response | 30 seconds   | 30 seconds                                                     |
| Subrequests per invocation                          | 50           | 10,000 by default                                              |
| Subrequests to internal services                    | 1,000        | the configured limit, 10,000 by default                        |
| Simultaneous outgoing connections per invocation    | 6            | 6                                                              |
| Cron Triggers per account                           | 5            | 250                                                            |
| Requests per day                                    | 100,000      | no limit                                                       |

What the pages say, and what they leave open:

- **Waiting doesn't count as CPU time.** Time spent waiting on `fetch`, KV or a database query does not count. Parsing and validating the responses does.
- **CPU time in `ctx.waitUntil` isn't covered.** No page says whether it counts toward the request's 10 ms. The plan assumes it does, so the on-save path shares the 10 ms of the `POST /save` request that started it.
- **D1's place in the subrequest limits isn't covered either.** A subrequest is any `fetch` or call to a Cloudflare service such as D1, but no page defines "internal services" or says which of the two limits a D1 query counts toward. The batch size below fits under 50 even if D1 queries count toward it.
- **The cron details.** No page states a minimum interval, and the smallest example schedule is every minute. No page says whether cron runs count toward the 100,000 requests per day. The sweep's schedule makes at most 288 runs a day, so either way they use little of that limit. Haystack uses one of the account's five Cron Triggers.

**The worst case for one bookmark is 10 outside requests and 3 D1 statements.** No page says whether a D1 `batch()` call counts as one subrequest or as one per statement, so every statement is counted. The count holds only if the clients make no retries of their own beyond these, so three rules come with it:

- **Jev:** the Jev client (#122) makes at most 3 attempts per question, and gives each attempt a time limit.
- **LLM:** each `enrich()` call makes exactly one HTTP request, with a time limit. The Anthropic SDK retries failed requests twice by default, so the Anthropic and AI Gateway adapters (#124, #125) turn its retries off (`maxRetries: 0`) or use plain `fetch`. A failure is classified as transient or permanent, as "The provider interface" describes, and left to the sweep.
- **GitHub:** the GitHub client (#123) makes its 2 requests once each, with its time limit and no retries. It makes only the first when the repository can't be read, so 2 is the most (see "GitHub enrichment").

With those rules, the outside requests are:

- up to 3 attempts at the sensitivity question
- 2 GitHub requests, for the repository and its README
- up to 3 attempts at the `kind` question
- 2 LLM calls, when the first output fails validation and the module retries once

The 3 D1 statements record the noul, and then either write the enrichment and delete the failure record in one batch, or write the failure record. On top of that, each run makes up to 8 D1 statements and reads 2 flags:

- the selection query
- the `match_text` refresh, which reads at most 4 enrichments at an older derivation version and rewrites them in one D1 `batch()` call, 5 statements in all. A larger refresh, after `match_text_version` is raised, takes several runs (#127). At the hourly steady state that is slow: 200 enrichments take 50 hours, and search judges bookmarks on two derivations in the meantime. So when `match_text_version` is raised, move the schedule back to every 5 minutes until the refresh is done, which rewrites up to 1,152 a day.
- the two cleanups, of expired sessions and of expired `auth_flows` rows
- the flags for the sweep's enabled switch and its batch size. The Flagship documentation suggests a flag read is not a subrequest (Q13), but each is counted as one anyway.

**The sweep starts at 3 bookmarks a run, every 5 minutes.** In the worst case, 3 bookmarks make 3 × 13 = 39 subrequests, and the run's own 10 bring the total to 49, under 50 even if every D1 statement and flag read counts. A fourth bookmark would make it 62. The batch size flag's default in the configuration module is also 3 (#128), so a Flagship outage can't push a run over the limit. The 3 bookmarks can run at the same time. A seventh simultaneous connection would wait for one of the six to finish rather than fail, so concurrency affects only how long a run takes. At every 5 minutes (`*/5 * * * *`), the backlog drains at up to 864 bookmarks a day, which is more than Milestone 1 saved. Once the backlog is empty, #133 moves the schedule to hourly, unless the on-save path is dropped (below). The schedule is the Cron Trigger's `triggers.crons` entry in `wrangler.jsonc`, so changing it needs a deploy (#128 corrects "Secrets and configuration" and Phase 8, which both call it a `var`). The batch size is a Flagship flag, so it can be lowered without one, and the configuration module ignores a value above 3 (see "Secrets and configuration").

**CPU time is the limit that only measurement can settle.** In production, `POST /save/address`, which reads a page's head before redirecting to the save form, used 6 to 8 ms of CPU time (#105). That request does no enrichment, but it shows that parsing responses can come close to 10 ms. #130 records each sweep run's CPU time from the tail. If a run is cut off for exceeding its CPU time, or comes within 2 ms of the limit, lower the batch size. The limits page says a run that is cut off has the outcome `exceededCpu` in analytics and Logpush, and shows as "Exceeded CPU Time Limits" in the dashboard's invocation statuses. The subrequest limit keeps the batch size from going above 3 on Workers Free. If Cloudflare documents that D1 queries count only toward the 1,000, the limit rises to 4, because 4 bookmarks then make at most 4 × 10 + 2 = 42.

**The on-save path has its own risk.** Under the plan's assumption above, it shares the 10 ms of its `POST /save`, which also asks Jev the sensitivity question from Phase 9 (#132). The bookmark is written before the response is sent, so a run cut off in `ctx.waitUntil` loses nothing, and the sweep enriches the bookmark later. But then the bookmark isn't enriched within seconds. #133 measures this. If saves often go over, Schalk chooses one of three fixes: move to Workers Paid (Q1), keep the sweep at every 5 minutes and drop the on-save path, or both. Without the on-save path, a new bookmark is enriched by the next sweep run, within about 5 minutes, and Phase 9's acceptance uses that bound instead.

**Q4. Extension background model.** Firefox and Chrome differ in how Manifest V3 declares background scripts. The v1 design avoids a background script by doing everything in the action popup, which opens the save form with `tabs.create` and then closes itself. Confirm this works in both browsers. _Blocks Phase 5._

_Chrome half confirmed in #70, in Playwright's Chromium (Chrome for Testing 156) headless, with Playwright 1.64:_

- A popup-only Manifest V3 extension works. The manifest has `action.default_popup`, the `activeTab` and `scripting` permissions, and no `background`, `host_permissions` or `content_scripts` keys. When the toolbar action runs, the popup reads the active tab's URL and title, `scripting.executeScript` reads `document.title`, `tabs.create` opens `/save`, and the popup closes itself.
- The DevTools protocol command `Extensions.triggerAction({ id, targetId })` runs the toolbar action the way a click does, including the `activeTab` grant. It needs no extra flag: Playwright already connects over `--remote-debugging-pipe`, and `--enable-unsafe-extension-debugging` was not needed. `targetId` must be the tab's target (type `tab`, listed by `Target.getTargets` with the filter `[{ type: "tab" }]`), not the page target that Playwright uses; with a page target the command fails with "Action can only be triggered on a tab target".
- The extension has no service worker, so its ID comes from `Extensions.getExtensions`, which needs no flag either.
- The `browser` namespace exists with promises from Chrome 148, so the manifest sets `minimum_chrome_version` to 148 and the popup uses no polyfill.

**Q5. OAuth implementation.** Choose one of three approaches, with sessions stored in D1 in each case. The first is implementing the Google authorization code flow with PKCE directly, using Web Crypto to verify ID tokens against Google's published keys. The second is a small, maintained OAuth client library, with hand-written session handling. The third is Better Auth, which runs on Workers with D1 and handles sessions as well. With the extension no longer holding credentials, a single sign-in flow is all that is needed, so the second option is the recommendation: the session code is small and worth understanding fully. _Resolved again 2026-10-07: `oauth4webapi` for the authorization code flow with PKCE, `jose` for verifying signatures against Google's published keys if `oauth4webapi` does not do it, and hand-written sessions stored in D1. Both libraries are maintained by panva and list Cloudflare Workers as a supported runtime. The first resolution, on 2026-10-06, chose Arctic. Arctic was deprecated on 2026-07-29 (its README and npm say so; last release 3.7.0, May 2025), which CodeRabbit pointed out on #12._

Confirmed in #26 against `oauth4webapi` 3.8.8:

- It accepts explicit endpoint URLs: `AuthorizationServer` is a plain object, so every URL comes from `vars` and no discovery request is made.
- It does not verify the ID token signature during the code exchange. It checks the claims and relies on TLS to the token endpoint. `validateApplicationLevelSignature` verifies the signature against `jwks_uri`, and the callback calls it, so `jose` is not needed.
- Its `allowInsecureRequests` option (marked deprecated, documented for testing against non-TLS servers) is set only when every `http:` endpoint is on a loopback host, which is the test fixture's case.

_Answered 2026-10-22 (#118)._ Every source below was read on 2026-10-22, and Schalk accepted the terms as they stand.

- **TypeSafe, which runs Jev.** The [privacy policy](https://typesafe.ai/privacy) says TypeSafe will not train or fine-tune models on prompts or other input, and the [enterprise page](https://typesafe.ai/enterprise) says the same of inputs and outputs.
  - **Retention:** no period is given for API inputs and outputs. The privacy policy keeps personal data "for as long as reasonably necessary to provide you with the Services", and the [data processing agreement](https://typesafe.ai/legal/data-processing) keeps customer personal data "for as long as necessary taking into account the purpose of the Processing".
  - **Zero data retention:** the documentation's [Legal page](https://docs.typesafe.ai/legal) and the enterprise page offer it to enterprise customers through sales, with no published terms. Neither says whether an account that isn't an enterprise customer can have it, and Haystack hasn't asked.
  - **Why it's acceptable:** TypeSafe never sees more than Anthropic does. The sensitivity check sends only `describeUrlForJudgment`'s redacted description, never the URL, and the `kind` question sends the same captured data that the LLM receives.
- **Anthropic.** Haystack sends its enrichment prompts to `claude-haiku-5-5`, the model Schalk chose.
  - **Training:** inputs and outputs aren't used for training by default ([model training](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training)). The [Commercial Terms](https://www.anthropic.com/legal/commercial-terms) say Anthropic may not train models on customer content from the services.
  - **Retention:** the plan assumes 30 days, the longer of the two readings. The [privacy center](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data) says inputs and outputs are deleted within 30 days. [API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) says they aren't kept by default, except for Covered Models, which require 30 days.
  - **Covered Models:** Claude Fable 5.1, Fable 5, Mythos 5.1 and Mythos 5 require 30-day retention and can't have zero data retention. Haiku 5.5 is not on the list.
  - **Flagged content:** whatever the arrangement, content flagged by Anthropic's trust and safety systems may be kept for up to 2 years, and its classification scores for up to 7.
  - **Zero data retention:** it is enabled per organization through Anthropic's sales team. Haystack has not asked for it.
- **GitHub** receives only the repository path, sent with a token that can read public repositories only (verified in #123, see "GitHub enrichment"). The [General Privacy Statement](https://docs.github.com/en/site-policy/privacy-policies/github-general-privacy-statement), effective 2026-04-27, says nothing specific about REST API requests. It does collect usage data automatically, including the IP address and the date and time of requests.
  - **Training:** the statement lists training models among the ways GitHub develops and improves its products with personal data, and it allows sharing personal data with affiliates, including Microsoft, for that purpose. The opt-out in section J.3 of the [Terms of Service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service) covers only the inputs and outputs of AI features such as Copilot, so no setting keeps request data out of training.
  - **Retention:** personal data is kept while the account is active and as needed for legal and contractual reasons, with no period stated.
  - **What GitHub learns:** which repository paths Haystack looked up, attributed to the token's account. A path can name a private repository, but the token can't read private repositories, so GitHub answers 404 and no private README leaves GitHub.
  - **Why it's acceptable:** GitHub already sees the same interest when a saved repository is opened while signed in. Schalk accepted this on 2026-10-22, after the training terms above were found.
- **Cloudflare AI Gateway.** [Logging](https://developers.cloudflare.com/ai-gateway/observability/logging/) is on by default for each gateway. A log can hold the prompt, the response, the provider, the time, the status, token usage, cost, duration and the user agent. The logging page says nothing about training on logged data.
  - **Retention:** an account whose first gateway was created on or after 2026-09-24 follows [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) retention, which is 3 days on Workers Free. An older account keeps [legacy logs](https://developers.cloudflare.com/ai-gateway/observability/logging/legacy-logs/) until they're deleted. Schalk confirmed that the account has no gateway from before 2026-09-24. The Workers Logs page says its pricing changes on 2026-12-01, so check the retention again then.
  - **Decision: log metadata only.** The gateway keeps its **Logs** setting on, so requests, status, tokens, cost and duration stay visible. The AI Gateway adapter sends `cf-aig-collect-log-payload: false` on every request, which drops the prompt and response bodies from the log. The documentation describes no gateway-wide setting for bodies, only this per-request header, so the adapter is where the decision lives. #125 tests that every request carries the header. A request without it would have its bodies logged for 3 days.
- **Later providers.** The OpenAI and OpenRouter adapters come after v1, and each needs the same check, recorded here, before it ships.

**Q8. MCP authorization.** Search-only lowers the blast radius, but the remote MCP server still needs authentication: search results are the user's private bookmarks, and every search spends Jev budget, so an open endpoint would expose both. The MCP specification's authorization model is OAuth-based. ## Data model

Use Drizzle with the D1 driver for the schema definition and all queries. Drizzle is a thin, SQL-shaped query builder, so queries stay close to the SQL below while gaining types inferred from the schema.

Migrations follow one path. `drizzle-kit generate` writes a SQL migration from changes to `src/db/schema.ts` into `apps/worker/migrations`, a person reviews the generated SQL, and `wrangler d1 migrations apply` is the only tool that applies migrations, locally and remotely. Never use `drizzle-kit push` or `drizzle-kit migrate`, because two tools applying migrations would disagree about what has been applied. `drizzle.config.ts` has no database credentials, so those commands cannot run.

Compatibility with Wrangler's migration tracking was confirmed in #7, on the stable lines (drizzle-orm 0.45, drizzle-kit 0.31) with Wrangler 4.147.0. Drizzle's [D1 page](https://orm.drizzle.team/docs/connect-cloudflare-d1) only says to set `migrations_dir` in the Wrangler configuration, and it already targets the Drizzle 1.0 release candidate. So the check used the tools themselves:

- drizzle-kit 0.31 writes flat files (`migrations/0000_init.sql`), plus its own `migrations/meta/` folder.
- Wrangler reads `migrations_dir/*.sql` by default (its `getD1MigrationFiles`), so it ignores `meta/`. It records each migration by file name in `d1_migrations`. Applying twice applies nothing the second time.
- Drizzle 1.0 writes one folder per migration (`migrations/<name>/migration.sql`). Wrangler 4.147.0 supports that layout through `migrations_pattern`, and it warns about Drizzle's layout by name when that option is missing. Wrangler records each migration by its path relative to `migrations_dir`, so the recorded names change with the layout. A move after the first production deploy therefore needs a planned rename of the rows in `d1_migrations`, described below (#13).

**Decision: the first production deploy stays on Drizzle 0.x (#13).** On 2026-10-18, npm's `latest` tag is drizzle-orm 0.45.4 and drizzle-kit 0.31.11, and Drizzle 1.0 is still a release candidate (the `rc` tag is 1.0.0-rc.4). Moving now would put the production migration history on a pre-release tool, so the project stays on the stable lines and accepts the rename below as the cost of moving later.

**When to revisit.** Revisit when `vp view drizzle-orm dist-tags.latest` and `vp view drizzle-kit dist-tags.latest` both print 1.0.0 or later. Check this at each milestone deploy, as with Q14 (when to move from Wrangler to `cf`).

**Moving to the folder layout later.** Without a rename, Wrangler treats every migration as unapplied after the move and runs it again. Wrangler 4.149.0 creates the tracking table as `d1_migrations(id INTEGER PRIMARY KEY AUTOINCREMENT, name TEXT UNIQUE, applied_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP NOT NULL)`, and a migration counts as applied only when its path appears in `name`. The steps were tested with drizzle-kit 1.0.0-rc.4 and Wrangler 4.149.0 on local databases, so repeat the test with the stable release before using them.

1. Take an export with `vp -C apps/worker run db:export:remote` (see "Backups and restore" below).
2. Upgrade drizzle-orm and drizzle-kit, then run `vp -C apps/worker exec drizzle-kit up`. It reads `drizzle.config.ts`, moves each flat file into a folder named from the migration's `when` timestamp in `meta/_journal.json` (in UTC) and its name, and deletes `meta/`. The SQL is unchanged. The current `0000_init.sql` becomes `20261009194159_init/migration.sql`. This step is required, because drizzle-kit 1.0's `generate` stops with "Your migrations folder format is outdated, please run drizzle-kit up" while the old layout is in place.
3. Add `"migrations_pattern": "migrations/*/migration.sql"` to the D1 binding in `apps/worker/wrangler.jsonc`, next to `migrations_dir`.
4. Rename each recorded row from its old file name to its new path, one `UPDATE` per migration, for example `vp -C apps/worker exec wrangler d1 execute DB --remote --command "UPDATE d1_migrations SET name = '20261009194159_init/migration.sql' WHERE name = '0000_init.sql'"`. Do the same for any local database worth keeping, with `--local` in place of `--remote`. Otherwise delete `apps/worker/.wrangler/state`.
5. Run `vp -C apps/worker exec wrangler d1 migrations list DB --remote`. It must print "No migrations to apply!".

Run step 4 right before or right after merging the change that converts the folder, and before any other remote `migrations apply`. The deployed Worker never reads `d1_migrations`, so the rename does not affect it. The hazard is a checkout on the other layout: after the rename, a checkout with the old layout sees every migration as unapplied, and its `migrations apply` fails on tables that already exist.

The test used two flat migrations and a fresh state directory for each case (`--persist-to`). A fresh database on the converted layout recorded each migration once, and a second `migrations apply` printed "No migrations to apply!". A database first migrated on the flat layout listed both migrations as unapplied after the switch. After the rename, `migrations list` and `migrations apply` both printed "No migrations to apply!", each migration was recorded once, and a row added before the switch was still there.

Name each migration, because the name is recorded in `d1_migrations` permanently: `vp run db:generate --name <slug>`. Without `--name`, drizzle-kit picks a random name.

From the first production deploy at the end of Milestone 1, the database holds real data. Every schema change after that point is a reviewed, forward-only migration. A destructive change (dropping or renaming a column) requires a note in the migration explaining what happens to existing rows.

Rolling back a Worker deployment does not roll back D1. Every migration must therefore stay compatible with the Worker version deployed before it (expand, then contract). Add a column or table in one deploy, and remove what it replaces in a later deploy, after nothing reads it. If a migration cannot stay compatible, it needs a written rollback procedure before it is applied.

The bookmarks exist only in the production database, so "Backups and restore" below says how it is protected and how to restore it (#91).

**Conventions.** All timestamps are `INTEGER` Unix epoch milliseconds, and application code sets them. Do not use `datetime('now')` defaults. SQLite's `datetime('now')` gives `2026-10-05 21:14:00`, and JavaScript's `toISOString()` gives `2026-10-05T21:14:00.000Z`. If both formats are compared as text, for example `expires_at < ?` in the session lookup, the comparison is wrong on the same day, because a space sorts before `T`. One numeric representation removes that type of bug. Application code generates IDs with `crypto.randomUUID()`. Cascading deletes need foreign key enforcement. D1 enforces foreign keys by default, equivalent to SQLite's `PRAGMA foreign_keys = on` ([D1 foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)). The deletion tests in `apps/worker/test/db.test.ts` prove the schema's delete behavior in the local runtime: deleting a user deletes their sessions, a user who still has bookmarks cannot be deleted, and deleting a bookmark deletes its enrichments and failure records.

D1 does not support interactive transactions. Where several writes must succeed or fail together, such as inserting an enrichment and clearing its failure record, use Drizzle's `batch`, which D1 executes atomically.

JSON columns use Drizzle's JSON text mode and are validated with Valibot when read, since the database does not enforce their shape. Valibot schemas for rows may be derived from the Drizzle schema if a maintained integration exists; check whether that is `drizzle-orm/valibot` or the separate `drizzle-valibot` package in the current versions. The capture payload and enrichment output schemas remain hand-written, because they describe external input rather than table rows.

The tables below describe the intended schema. The Drizzle schema must produce equivalent tables. Columns ending in `_at` are epoch milliseconds, as described under "Conventions."

```sql
CREATE TABLE users (
  id TEXT PRIMARY KEY,
  google_sub TEXT NOT NULL UNIQUE,     -- stable Google account ID; never key on email
  email TEXT NOT NULL,
  display_name TEXT,
  created_at INTEGER NOT NULL
);

CREATE TABLE sessions (
  id_hash TEXT PRIMARY KEY,            -- SHA-256 of the session ID; the raw ID lives only in the cookie
  user_id TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at INTEGER NOT NULL,
  created_at INTEGER NOT NULL
);

CREATE TABLE auth_flows (
  state_hash TEXT PRIMARY KEY,         -- SHA-256 of the OAuth state; single use
  code_verifier TEXT NOT NULL,         -- PKCE verifier
  return_to TEXT NOT NULL,             -- relative path and query, validated before redirect
  expires_at INTEGER NOT NULL,         -- short-lived, for example 10 minutes
  created_at INTEGER NOT NULL
);

CREATE TABLE bookmarks (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  url TEXT NOT NULL,                   -- as submitted, minus tracking parameters
  normalized_url TEXT NOT NULL,        -- see "URL normalization"; used for duplicates
  title TEXT NOT NULL,                 -- as confirmed on the save form
  description TEXT,                    -- as confirmed on the save form
  canonical_url TEXT,                  -- raw captured values below, kept as enrichment evidence
  captured_title TEXT,
  captured_description TEXT,
  og_title TEXT,
  og_description TEXT,
  og_site_name TEXT,
  sensitive_canonical_dropped INTEGER, -- Milestone 2+ (#79): 1 when a canonical URL that detectSensitiveUrl flags was dropped, 0 when none was, NULL when the save did not record it
  sensitivity_noul REAL,               -- Milestone 2+: Jev probability that the URL grants private access; NULL = not yet checked
  sensitivity_checked_at INTEGER,
  sensitivity_acknowledged_at INTEGER, -- set when the user confirms the link is not private (save form or /held)
  created_at INTEGER NOT NULL,
  UNIQUE (user_id, normalized_url)
);

CREATE TABLE enrichments (
  id TEXT PRIMARY KEY,
  bookmark_id TEXT NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,
  schema_version INTEGER NOT NULL,
  provider TEXT NOT NULL,
  model TEXT NOT NULL,
  kind TEXT NOT NULL,
  kind_probabilities TEXT NOT NULL,   -- JSON
  data TEXT NOT NULL,                 -- full validated enrichment JSON
  match_text TEXT NOT NULL,
  match_text_version INTEGER NOT NULL,
  created_at INTEGER NOT NULL,
  UNIQUE (bookmark_id, schema_version)
);

CREATE TABLE enrichment_failures (
  bookmark_id TEXT NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,
  schema_version INTEGER NOT NULL,
  attempts INTEGER NOT NULL,             -- permanent failures only; at the attempt limit the bookmark is Failed
  consecutive_failures INTEGER NOT NULL, -- every failure, transient or permanent; the sweep's backoff grows with it (#120)
  last_error TEXT NOT NULL,
  last_attempt_at INTEGER NOT NULL,
  PRIMARY KEY (bookmark_id, schema_version)
);

CREATE TABLE search_runs (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL REFERENCES users(id),
  query TEXT NOT NULL,
  channel TEXT NOT NULL CHECK (channel IN ('web', 'webmcp', 'mcp')),
  input_mode TEXT CHECK (input_mode IN ('typed', 'web-speech', 'whisper')),  -- web channel only; 'whisper' is reserved for the backlog item, so adding it needs no table rebuild
  request_mode TEXT NOT NULL CHECK (request_mode IN ('pair', 'batched')),
  jev_model TEXT NOT NULL,
  questions TEXT NOT NULL CHECK (questions IN ('both', 'noul', 'score')),  -- which Jev questions were asked
  display_signal TEXT NOT NULL CHECK (display_signal IN ('noul', 'score')),
  noul_threshold REAL NOT NULL,
  score_threshold REAL NOT NULL,
  input_tokens INTEGER,
  latency_ms INTEGER,
  outcome TEXT NOT NULL CHECK (outcome IN ('ok', 'partial', 'failed')),  -- partial: some chunks failed
  error TEXT,                          -- set when outcome is not 'ok'
  created_at INTEGER NOT NULL
);

CREATE TABLE search_answers (
  search_run_id TEXT NOT NULL REFERENCES search_runs(id) ON DELETE CASCADE,
  bookmark_id TEXT NOT NULL REFERENCES bookmarks(id) ON DELETE CASCADE,
  noul REAL NOT NULL,
  score REAL NOT NULL,
  score_probabilities TEXT NOT NULL,  -- JSON
  score_confidence REAL NOT NULL,
  shown INTEGER NOT NULL,             -- 0 or 1
  clicked INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (search_run_id, bookmark_id)
);
```

The `search_answers` table stores every answer for every candidate, including those below the threshold. This is what makes offline threshold replay possible without calling Jev again. Clicks are recorded as a weak relevance label. A search that fails, completely or for some chunks, is still logged in `search_runs` with its `outcome` and `error`. Without these rows, the logs show no Jev outages, and failed searches look like searches nobody made.

### Enrichment state is derived, not stored

There is no `status` column. A stored status would have to be kept in sync with the enrichments table, and it becomes ambiguous during a schema version change. Instead, a bookmark's enrichment state is computed from its sensitivity columns and the two enrichment tables:

| State    | Condition (evaluated in this order; the first match wins)                                                                                                                                                                     |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Held     | Its `sensitivity_noul` is at or above the warning threshold and `sensitivity_acknowledged_at` is not set. It is excluded from search and never sent to the LLM provider, GitHub, or the `kind` question until it is released. |
| Current  | It has an enrichment at the current `schema_version`.                                                                                                                                                                         |
| Failed   | It has reached the attempt limit at the current version. It needs manual attention. If it has an enrichment from an older version, it stays searchable through that one.                                                      |
| Outdated | It has an enrichment at an older version only. It is still searchable, and the sweep will re-enrich it.                                                                                                                       |
| Pending  | It has no enrichment at any version.                                                                                                                                                                                          |

Attempts are counted per schema version, so raising the version automatically gives previously failed bookmarks a fresh set of attempts.

Held is evaluated against the current `SENSITIVE_WARN_THRESHOLD`, not against the threshold that applied when the bookmark was checked. If the threshold is lowered, Current bookmarks above the new value become Held and leave search until they are released. This is intentional. It is the conservative direction, and the `/held` page shows them. Raising the threshold releases them automatically.

**Search uses each bookmark's most recent enrichment, whatever its version**, and never includes Held bookmarks. A schema version change therefore never removes anything from search. Bookmarks keep their old enrichment until the sweep replaces it. Only bookmarks with no enrichment at all are left out of search.

**One function derives the state (#120).** `deriveEnrichmentState`, in `apps/worker/src/enrichment/state.ts`, is a pure function. It takes the bookmark's `sensitivity_noul` and `sensitivity_acknowledged_at`, the schema version of each of its enrichments, and its failure record at the current version, together with the version that record was read at. It also takes the current `schema_version`, the warning threshold and the attempt limit as arguments, and it checks the table's conditions in the table's order. It throws when the inputs were read at a different version from the one it is given, because the bookmark's failure record at the current version would then be missing, and it could never be Failed.

`readEnrichmentStateInputs`, in `apps/worker/src/enrichment/state-inputs.ts`, reads those inputs for one user's bookmarks in a single query, so `/held` and search do not each assemble them. The sweep (Phase 8) needs its own query, because it reads every user's bookmarks and its backoff also needs the failure record's `last_attempt_at` and `consecutive_failures`. That query reuses `collectStateInputs`, from the same file, which turns the joined rows into one set of inputs per bookmark and keeps any extra columns the query selected, so the two queries cannot build the inputs differently.

The function decides three cases that the table leaves open:

- A bookmark whose `sensitivity_noul` is `NULL` is never Held, because it has not been checked yet. The enrichment module checks it first.
- A failure record below the attempt limit does not make a bookmark Failed. That includes a record of transient failures only, whose `attempts` is 0.
- An enrichment at a version newer than the current one counts as Outdated, as an older one does. That happens only after the Worker is rolled back past a schema version change. Outdated keeps the bookmark searchable while the sweep enriches it at the current version, and calling it Pending would be wrong, because it has an enrichment.

### URL normalization

`normalized_url` is derived in code, and is used only for duplicate detection. The stored `url` is what the bookmark links to. It is the submitted URL with tracking parameters removed by `stripTrackingParameters`, which uses the same tracking list as normalization. Everything else stays as submitted: case, encoding, parameter order, the trailing slash, and the fragment. `GET /save` shows the stripped URL on the form, and `POST /save` strips again before storing, because the hidden input can be tampered with. Changing the tracking list affects new saves only. Stored `url` values are not recomputed, and that difference is intentional: an old link that still has a tracking parameter works the same. Pairs are split on `&` only, so with `?utm_source=x;b=1` the whole pair is removed, including `b=1`. The same is true for normalization. (Added 2026-10-11.) Normalization lowercases the scheme and host, removes default ports, removes the fragment, removes common tracking parameters (`utm_*`, `fbclid`, `gclid`, and similar, as an explicit list), sorts the remaining query parameters, and removes a trailing slash from the path. It is a pure function in `packages/schemas`, with a table of test cases.

The function is `normalizeUrl` (#19). Details that are part of the rules, so changing them also needs the migration described below:

- It removes credentials (`user:pass@`). Such URLs are refused by `detectSensitiveUrl` anyway.
- The tracking list is `TRACKING_PARAMETERS`, plus every `utm_*` key, matched case-insensitively on the decoded key.
- Query pairs keep the encoding the URL parser gives them, and are sorted by decoded key. Pairs with the same decoded key keep their order.
- It rejects anything other than `http` and `https`.
- It is applied to the URL as submitted, never to a stored normalized value. It is not idempotent for paths that end in several slashes.

`normalized_url` is stored, so a change to the normalization function (for example, a new tracking parameter in the list) makes existing rows out of date. When recomputed, two existing bookmarks can collide on `UNIQUE (user_id, normalized_url)`. Such a change therefore needs a migration that recomputes the column and states how collisions are resolved (keep the oldest bookmark, and report the others). It is not a code-only change.

Two submissions of the same URL can race, for example from two tabs. The second insert then fails on the unique constraint. `POST /save` must show the "already saved" result for that case, not an error page.

### Backups and restore

Two things protect the production database: D1's point-in-time recovery (Time Travel) for the last 7 days, and an export, taken before each remote migration and at least once a week, for anything older (#91). Every command below runs from the repository root, and Wrangler finds `DB` through `apps/worker/wrangler.jsonc`. The commands and flags were checked against Wrangler 4.149.0's `--help` and source.

**Time Travel retention.** The account is on Workers Free, so Time Travel can restore the database to any minute in the last 7 days. Workers Paid allows 30 days ([Time Travel](https://developers.cloudflare.com/d1/reference/time-travel/)). If the account moves to Workers Paid (Q1, which decides the Workers plan), change the window in this section to 30 days. The procedure stays the same. A restore overwrites the database in place and cancels queries in flight. It cannot restore into a new database. It returns a bookmark for the state before the restore, so a restore can be undone. Wrangler itself accepts any time in the last 30 days whatever the plan, because that check runs on the client. On Workers Free, Cloudflare refuses a time between 7 and 30 days ago.

**Export before each remote migration, and once a week.** Run `vp -C apps/worker run db:export:remote` before every `vp -C apps/worker run db:migrate:remote`, which applies the migrations to the production database. Also run it at least once a week, so that the newest export is never older than the 7 days Time Travel covers. A restore from an export loses every row written after it, so an export taken only before migrations could be months old. It writes two files with the same UTC timestamp to `apps/worker/backups/`: `haystack-<timestamp>-schema.sql` (from `--no-data`) and `haystack-<timestamp>-data.sql` (from `--no-schema`). The files hold every user, session and bookmark row, so `.gitignore` keeps that folder out of the repository. They exist only on the machine that ran the script, so right after each export, copy both files somewhere off that machine that only you can read. Otherwise losing the machine, or the checkout, loses the only copy older than 7 days. #92 decides where that is, and whether the copy can be automated. An export blocks other queries to the database while it runs. Wrangler would ask for confirmation before each export, but the script passes `--skip-confirmation`, because answering no to the first would still run the second and leave a data file without its schema file. Because Time Travel reaches back only 7 days, these files are the only copy of anything older. Wrangler's help for `migrations apply` says a backup is captured after applying, but the 4.149.0 source takes none, so the script is the only backup step.

The export is split in two because a single full export cannot be imported. It lists tables in alphabetical order, so the `bookmarks` rows come before the `users` table they reference, and the import fails with "no such table: main.users". Adding `PRAGMA foreign_keys=OFF` to the top of the file did not help in the local test either. Importing the schema file first and the data file second works.

**Restoring with Time Travel, for a problem less than 7 days old.**

1. **Find the restore point.** Record the current bookmark first, so there is a way back even if the restore output is lost: `vp -C apps/worker exec wrangler d1 time-travel info DB`. Then get the bookmark for a time just before the problem: `vp -C apps/worker exec wrangler d1 time-travel info DB --timestamp=<time just before the problem>`. Replace the placeholder with that time, as an RFC 3339 string such as `2026-10-18T09:00:00Z` or as Unix seconds (10 digits). A time that is too late keeps the damage, and one that is too early rolls back good writes.
2. **Restore.** `vp -C apps/worker exec wrangler d1 time-travel restore DB --bookmark=<bookmark>`. `--timestamp=<time>` works in place of `--bookmark`, but not together with it. Wrangler asks for confirmation, then prints the bookmark it restored to and the previous bookmark. Keep the previous bookmark.
3. **Check the result.** Count the rows and compare them with what you expect: `vp -C apps/worker exec wrangler d1 execute DB --remote --command "SELECT count(*) FROM bookmarks"`. Then run `vp -C apps/worker exec wrangler d1 migrations list DB --remote`. The restore also rolls back `d1_migrations`, so a migration applied after the restore point shows as unapplied again. If the deployed Worker needs it, apply it again, or roll the Worker back to the version that matches the restored schema.
4. **Undo the restore** if the result is wrong: `vp -C apps/worker exec wrangler d1 time-travel restore DB --bookmark=<previous bookmark>`.

**Restoring from an export, for a problem 7 days old or more.** Time Travel cannot reach that far back. Import the newest export from before the problem into a new database, and leave the current one untouched until the new one is confirmed. **Every row written after that export is lost**, which is why the export runs weekly. To keep newer rows, take a data-only export of the current database first (`vp -C apps/worker exec wrangler d1 export DB --remote --no-schema --output=backups/haystack-current-data.sql`), and copy the rows that the old export lacks into the restored database by hand. The files cannot be imported into the existing database, because their `CREATE TABLE` statements fail on tables that already exist ("table `auth_flows` already exists").

1. **Create a database.** `vp -C apps/worker exec wrangler d1 create haystack-restore-<date>`. It prints the new `database_id`.
2. **Import the schema, then the data.** `vp -C apps/worker exec wrangler d1 execute haystack-restore-<date> --remote --file=backups/haystack-<timestamp>-schema.sql`, then the same command with the `-data.sql` file. The paths are relative to `apps/worker`. Wrangler finds a database that is not in `wrangler.jsonc` by its name. The two files also restore `d1_migrations`, so Wrangler knows which migrations the restored database already has.
3. **Switch the binding.** Set `database_name` and `database_id` of the `DB` binding in `apps/worker/wrangler.jsonc` to the new database. Then run `vp -C apps/worker run db:migrate:remote` to apply the migrations that came after the export.
4. **Check the result** with the same commands as step 3 of the Time Travel restore.
5. **Commit, merge and deploy the switch promptly.** `wrangler.jsonc` is a committed file, so a deploy from a checkout of `main` without the change would point the Worker back at the old database. Until the deploy, the Worker keeps writing to the old database, and those rows are not in the new one. Keep the old database until the restored one has been in use for a while.

This path was tested locally with a seeded database: the two files, exported with `--local` and imported into a fresh database with `--persist-to`, kept every row and every quote in the data, `PRAGMA foreign_key_check` found nothing, and `migrations list` printed "No migrations to apply!". A migration applied afterwards was recorded once, with the next ID. The restored database has two `sqlite_sequence` rows for `d1_migrations`, one from each file, which is harmless because SQLite reads the first. The remote import goes through D1's import API instead, which was not tested.

## Enrichment design

### Captured payload from the extension

The extension puts the URL, the canonical URL if present, `document.title`, the meta description, and the Open Graph title, description, and site name into the `/save` query string. The same Valibot schema in `packages/schemas` validates the payload twice: in the extension before building the URL, and on the server for both the GET prefill and the POST submission. Every field except the URL is optional, and strings are trimmed and length-capped. The extension truncates to the same caps so the save URL stays well within URL length limits. The URL must use the `https` scheme. The canonical URL, if present, must use `http` or `https`. _Changed 2026-10-13 (#40): Haystack saves only `https` pages, so every saved address can be shown as a link (Phase 4). The canonical URL is only enrichment evidence and is never linked, so an `http` one does not stop a page from being saved._

The schema is `CapturePayload` in `packages/schemas` (#18):

- **Query keys:** `url`, `canonical_url`, `title`, `description`, `og_title`, `og_description`, `og_site_name`. Unknown keys are dropped.
- **Caps (`CAPTURE_CAPS`):** 2,048 for both URLs, 200 for the titles, 300 for the descriptions, and 100 for the site name.
  - The caps count UTF-16 code units (`String.prototype.length`), so an emoji counts as 2.
  - Text containing a lone surrogate is rejected, because `encodeURIComponent` throws on it.
  - The extension truncates without splitting a surrogate pair, with `truncate` from `packages/schemas` (#72). The Worker uses the same function when the address is the title's fallback. When a cut would fall inside a pair, the whole pair is dropped, so the result is one code unit under the cap.
- **Over-cap values are rejected, not truncated.** The extension truncates the text fields to the exported caps before validating, after trimming them so the cap counts what the schema keeps. It never truncates `url` or `canonical_url`: an over-cap `canonical_url` is dropped, and the page is still saved. A `canonical_url` that `detectSensitiveUrl` flags is dropped too (see "Sensitive URLs").
- **Empty values:** an optional field that is empty after trimming is left out of the result, not set to `undefined`.
- **The URL** keeps its submitted form, apart from trimming. The Worker then removes tracking parameters before showing and storing it (see "URL normalization"). Because the stored string must be what the URL parser reads, a URL is rejected when it:
  - contains a control character, tab, newline, or space (the parser strips or percent-encodes them; browsers already send spaces as `%20`)
  - does not start with an explicit `https://` (for the canonical URL, `http://` or `https://`). `https:example.com` parses, but as a link it resolves against the page's own origin.

The caps alone do not keep the save URL under Cloudflare's 16 KB URL limit:

- Text percent-encodes to up to 9 characters per code unit.
- The extension sends both URLs as serialized by `new URL(…).href`, which is ASCII, and an ASCII character encodes to at most 3. The 2,048 cap applies to that serialized form, so a URL that passes validation encodes to at most 6,144 characters. Serializing can make a URL much longer than the original (each non-ASCII character becomes up to 9 ASCII characters), so the extension validates the serialized form, not the original.
- At full caps, the save URL can still reach about 22,000 characters.

The extension (Phase 5) therefore measures the encoded save URL, whole, with the origin and `/save?` counted (#73). Above 8,000 characters (`SAVE_URL_BUDGET` in `packages/schemas`), it drops optional fields in this order until the URL fits: `og_description`, `description`, `og_title`, `og_site_name`, `canonical_url`. It stops as soon as the URL fits, and the title is never dropped. A `url` that passes validation fits on its own, and so does a `url` with the longest title, unless the origin is long (see "Built in #73"). The extension never truncates `url` or `canonical_url`, because a shortened URL can point somewhere else:

- A serialized `canonical_url` over its cap is dropped.
- A serialized `url` over its cap means the page cannot be saved. The popup says the address is too long to save, and no tab is opened.

Since #105, the Worker builds a save link too, for the address form, so the steps that the extension and the Worker share are in `packages/schemas`. `capturedFieldsFromPage` turns what a page says about itself into the payload to validate: it trims each text field, cuts it to its cap with `truncate`, and serializes the canonical URL without cutting it. `saveUrlWithinBudget` builds the save link within `SAVE_URL_BUDGET`, dropping fields in the order above. The budget rule and the order must change together in both places, so there is one implementation of each.

### GitHub enrichment

For repository URLs, call `GET /repos/{owner}/{repo}` and `GET /repos/{owner}/{repo}/readme`. Keep a README excerpt of roughly the first 2,000 characters, with Markdown syntax stripped. Use a `GITHUB_TOKEN` secret to avoid the low rate limit for unauthenticated requests. A GitHub failure must not fail the bookmark. Fall back to the captured payload.

The token must have read access to public repositories only. If it can read Schalk's private repositories, a bookmarked private repository would have its README fetched and sent to the LLM provider. A fine-grained token with no repository access grants exactly public read access (verify this against the current GitHub documentation when the token is created).

Matching is narrower than "any `github.com` URL". Only the first two path segments identify the repository, and the first segment must not be a reserved GitHub route such as `features`, `orgs`, `settings`, `marketplace`, `topics`, or `sponsors` (keep the list explicit in code). A URL deeper than the repository root, such as an issue, a pull request, or a file, is a bookmark of that page, not of the repository. For those URLs, give the repository data to the LLM as context for the page, labeled as such, so that an issue bookmark is not summarized as the repository.

_Built 2026-10-22 (#123)._ The matcher is `matchGitHubRepository` in `apps/worker/src/enrichment/github-url.ts`, and the client is `readGitHubRepository` in `apps/worker/src/enrichment/github-client.ts`. Nothing in production calls them yet: the enrichment module (#126) is the first caller. The endpoints, headers, media types and statuses come from GitHub's documentation, all read on 2026-10-22: [Get a repository](https://docs.github.com/en/rest/repos/repos#get-a-repository), [Get a repository README](https://docs.github.com/en/rest/repos/contents#get-a-repository-readme), [Getting started with the REST API](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api), [API Versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions), [Breaking changes](https://docs.github.com/en/rest/about-the-rest-api/breaking-changes), [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api) and [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens).

- **What matches.** Only `https://github.com/{owner}/{repo}` and the pages below it match, with no port and no credentials in the URL. A trailing slash, a query such as `?tab=readme-ov-file`, a fragment and a `.git` suffix still mean the repository's own page. An owner-only URL, `gist.github.com`, any other host and a first segment from the reserved list don't match. The owner may have letters, digits, `-` and `_`, up to 39 characters, and the repository letters, digits, `.`, `-` and `_`, up to 100 characters. The REST reference documents no naming rules, so these are Haystack's own and deliberately loose. They exist so that the request path needs no encoding, and so that a path that can't be a repository isn't sent.
- **The reserved routes** are `RESERVED_GITHUB_ROUTES`, 60 first segments compared in lower case. They come from the first segments of every page in GitHub's [marketing sitemap](https://github.com/sitemap_marketing.xml), the first segments that GitHub's [robots.txt](https://github.com/robots.txt) disallows (with the exceptions below), the six this section names, and other routes of the github.com app. Every one was checked against the REST API's `GET /users/{username}`, which answered 404, so no account has the name, and reserving it can't hide a repository. Two are reserved although an account has the name, because github.com serves GitHub's own pages under it: the sitemap shows GitHub's stories under `customer-stories`, and `github.com/biztools` redirects to `/biztools/coupons`, which asks for sign-in, while the `biztools` account has no public repository. robots.txt also disallows `/account-login`, but it isn't reserved, because the `account-login` account has 21 public repositories, and `github.com/account-login/bashrc` serves one of them. Names where GitHub serves a page but an account also exists, such as `watching` and `achievements`, are left out for the same reason, and so are the sitemap's `github`, which is GitHub's organization, and the two accounts that robots.txt names. A test keeps its own list of 24 routes that must stay reserved, so removing one from the code fails it. A route missing from the list costs only the 2 requests, which answer 404.
- **How a page within a repository is labeled.** The matcher returns `bookmark: "repository"` for the repository's own page and `bookmark: "page"` for anything deeper. The client turns that into `bookmark_is`, either `"the repository"` or `"a page within the repository"`, in the evidence it returns, so the model reads the label next to the repository's data.
- **The evidence**, `GitHubEvidence`, is the `kind` question's `github` state and the LLM's GitHub evidence: `repository` (`owner/repo`, as the bookmark's URL names it), `bookmark_is`, and `description`, `topics`, `language` (the primary language) and `readme_excerpt` when GitHub has a value. `askKind`'s `KindEvidence.github` is typed `object`, which accepts it, so its type is unchanged. The description is cut to 500 characters, the language to 100, and the topics to the first 20 of up to 50 characters each, which is GitHub's own limit for topics ([Classifying your repository with topics](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics)). GitHub documents no limit for the description.
- **The requests** are `GET {GITHUB_API_BASE_URL}/repos/{owner}/{repo}`, then `GET …/readme`, with `authorization: Bearer <GITHUB_TOKEN>`, `user-agent: Haystack (+https://github.com/schalkneethling/haystack)` and `x-github-api-version: 2026-03-10`. GitHub rejects a request without a User-Agent and asks for the application's name. The sweep runs without a request, so the page lookup's `Haystack (+<origin>)` can't be used, and the project's repository names Haystack instead. 2026-03-10 is the newest API version. A request without the header gets 2022-11-28, which is supported until 2028-03-10, and none of 2026-03-10's breaking changes touch the fields read here. Only the repository's path is sent: never the bookmarked URL, its query or the page within the repository (Q7). The two requests run one after the other, because the README is asked for only once the repository has been read and is public.
- **The README** is read with the raw media type, `application/vnd.github.raw+json`, which returns the file's own text. The default media type is JSON with the content in base64, which has to be downloaded whole, and the HTML media type is much larger than the Markdown for the same text. Only the first 16 KiB (`GITHUB_README_READ_LIMIT_BYTES`) are read from the stream, and the rest is cancelled. A README often starts with badges, logos and HTML that leave no text, so the limit is several times the excerpt. When the limit cuts the README, its last line, which may end in the middle of a link, is left out.
- **Removing the Markdown** is `readmeExcerpt` in `apps/worker/src/enrichment/readme-excerpt.ts`, with no new dependency. It isn't a parser. It removes the syntax that READMEs use: YAML front matter, headings, emphasis, links (their text is kept, with one level of brackets inside it), autolinks (their address is kept), images and badges (their alternative text stays on one line, so a `![` that nothing closes doesn't take the prose after it), code fences (removed with their code, which says little about what a repository is for; a line such as ` ```npm install foo``` ` isn't a fence, because CommonMark 0.31.2, section 4.5, allows no backtick in a backtick fence's info string, so it is a code span and its text is kept, while a tilde fence's info string may hold backticks), inline code (its text is kept, and protected first, so a `<!--` or a tag in a code span stays text, and, as in CommonMark, a code span never crosses a blank line, a heading, a list item or a removed block, so a stray backtick can't swallow the Markdown of the paragraphs after it), block quotes and alerts, lists, tables, rules, reference definitions, footnotes, backslash hard line breaks, HTML tags, comments, and `script`, `style` and `svg` elements, and it decodes character references with `entities`, which the Worker already uses. A construct cut off by the read limit is removed to the end. The excerpt keeps line breaks between blocks and is cut to 2,000 characters with `truncate`. The CPU time grows with the README's length and not faster. No pattern can share one run of characters between two of its parts in more than one way, none follows a run of any length with a backreference to it, and a pattern that isn't anchored stops at the next character that could end what it matches. Code spans and a heading's closing `#`s are found by hand, because the patterns for them were the quadratic ones. The review of 09bad9d found three patterns that broke this: the code span pattern took 278 ms on `a` followed by 16,383 backticks, the table delimiter pattern 123 ms on 16,383 spaces and an `x`, and the closing `#` pattern 128 ms on a heading of 16 KiB of spaces. With the current patterns, measured in Node 24 on an Apple M3 Pro, each of the 21 hostile shapes in `readme-excerpt.test.ts` takes under 2.5 ms, and the slowest, a backtick on every other line of 16 KiB, takes 2.2 ms. The tests time each shape 5 times and check the fastest against 50 ms, which the old patterns fail. The fastest is checked because a busy machine slows some calls down, but a quadratic pattern makes every call slow. The Worker's own time, in workerd, wasn't measured, and #130 records the sweep's CPU time.
- **Placeholders can't be forged.** While the syntax is removed, punctuation that must stay text, escaped with a backslash or inside a code span, is held as a private use character from U+E000 to U+E07F. Any such character already in the README is removed first, and so is a numeric character reference to one, before references are decoded. At the end, only a placeholder for punctuation is turned back, and any other character in that range is dropped, so a README can't produce a control character or reintroduce syntax this way.
- **Known limits of the stripper.** An indented code block is kept as text, because it can't be told apart from a list item's continued lines without parsing. Link text with brackets nested more than one level deep isn't recognized, so such a link stays as written. A tag with `>` inside a quoted attribute leaves the rest of the attribute behind.
- **The time limit** is 3 seconds per request, from the request to the last byte read (`GITHUB_REQUEST_TIMEOUT_MS`), the same as the page lookup. Both answers are small, and GitHub's documentation gives no response times. The two requests therefore add at most 6 seconds to a bookmark. For the on-save path (#132, measured in #133), that comes on top of the Jev questions, which already go past `ctx.waitUntil`'s 30 seconds in their worst case (see "Jev client"), so the on-save caller must pass shorter timings or accept being cut short, and the sweep enriches the bookmark later.
- **Nothing is retried,** as Q3 requires, so a `5xx` or a timeout reaches GitHub exactly once. A failure of the repository request returns no data, and a failure of the README request still returns the repository's data, with the README's failure alongside for logging. Each failure is a fixed code: `timeout`, `network`, `not-found` (a 404, which is also what a private repository gets), `rate-limited` (every 403 and 429, see below), `status` (any other status, which the result holds), `invalid-response`, and `private` (below).
- **A renamed repository gets no data.** GitHub answers `301` for the old path. The client doesn't follow redirects, so the token can't be sent on, and following one would be a third request that Q3 doesn't count.
- **A repository that isn't public stops the client.** A repository is public only when `private` is false and `visibility`, when GitHub sends it, is `public`. The OpenAPI description's `full-repository` schema ([github/rest-api-description](https://github.com/github/rest-api-description)) gives `visibility` as "public, private, or internal", and documents `private` only as whether the repository "is private or public", so `private` alone doesn't rule out an internal repository. An unknown `visibility` counts as not public too. If GitHub answers for any other repository, the token can read more than it should. The client then doesn't ask for the README and returns nothing, so a private or internal README is neither fetched nor sent to the LLM, whatever the token's settings.
- **The rate limit is shared.** All of a user's personal access tokens share 5,000 requests an hour. The sweep makes at most 72 GitHub requests an hour (3 bookmarks every 5 minutes), so Haystack alone stays far below it. GitHub warns that continuing to make requests while rate limited can get an integration banned. A secondary rate limit can come as a 403 or a 429 with neither `retry-after` nor `x-ratelimit-remaining: 0`, and then GitHub asks for a wait of at least a minute, so the headers can't tell it apart from any other 403. For a public repository read with a token that reads public repositories, GitHub documents no other 403, so the client reports every 403 and 429 as `rate-limited`. The caller makes no more GitHub requests for the rest of the run after any `rate-limited` failure, which #127 tests. A 403 for some other reason costs only that run's GitHub data. For GitHub, the rule #127 decides for rejected credentials therefore applies to a `401`.
- **The README is untrusted.** It only becomes text, nothing in it changes what the client does, and it reaches the LLM and Jev only as data (see "Untrusted content"). Nothing is logged. The token goes only in the `authorization` header, only to `GITHUB_API_BASE_URL`, only over https, or http on a loopback host for tests, and is never in a result. The client throws for an empty or missing token (`GITHUB_TOKEN_EMPTY`) and for a base URL that is neither, before sending anything, because those are configuration errors. The loopback exception is `isHttpsOrLoopbackUrl` from `@haystack/schemas`, the rule Google sign-in's endpoints use, so the integration tests can point the base URL at their plain-http server on `127.0.0.1` (Q10).
- **Tests** answer every request from `apps/worker/test/github-fixture.ts`, which uses MSW as the Jev fixture does and fails any request it didn't plan for.
- **The preferred README isn't always Markdown.** GitHub returns a README in reStructuredText or AsciiDoc too, and `readmeExcerpt` removes only Markdown, so some of their markup stays in the excerpt.

_The token's scope, verified 2026-10-22 (#123)._ The plan's expectation holds, with one correction of wording: the documentation has no "no repository access" setting, and instead says that every fine-grained token includes public read access.

- **Public repositories are always readable.** [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) says under "Repository access": "You should choose the minimal repository access that meets your needs. Tokens always include read-only access to all public repositories on GitHub."
- **No permission is needed for the two endpoints on a public repository.** The reference for each says "This endpoint can be used without authentication or the aforementioned permissions if only public resources are requested." The permissions it names are needed only for private repositories: "Metadata" (read) for "Get a repository", and "Contents" (read) for "Get a repository README". [Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens) lists both endpoints the same way and says "These permissions are required to access private resources."
- **A private repository answers 404.** [Troubleshooting the REST API](https://docs.github.com/en/rest/using-the-rest-api/troubleshooting-the-rest-api) says "If you make a request to access a private resource and your request isn't properly authenticated, you will receive a `404 Not Found` response", which GitHub uses "to avoid confirming the existence of private repositories".
- **The token Schalk creates** is a fine-grained personal access token: Settings, Developer settings, Personal access tokens, Fine-grained tokens, Generate new token. The resource owner is Schalk's own account. Repository access is the most minimal option, the one that selects no repository and leaves only the public read access every token has. The documentation doesn't name that option, so check in the form that it describes read-only access to public repositories, and never choose "All repositories", or "Only select repositories" with a repository selected. No permissions are added. It has an expiration, which the documentation recommends, so rotating it before then needs `wrangler secret put` again.

### Jev ingestion questions

A single Jev request with the combined captured and GitHub data as state asks one question, `kind`, a Choice with options such as `repository`, `library`, `tool`, `article`, `reference`, `video`, and `other`. Each option gets a short description in the criteria, and the `other` option exists so that a no-match outcome is always available.

Write the exact wording only after reading the Choice page in the live documentation. Store both the chosen `kind` and its full probability distribution.

The example options mix two dimensions. `repository` describes where a resource is hosted, while `library` and `tool` describe what it is. A GitHub repository of a test runner is correctly both `repository` and `tool`, so the distribution would split between them for reasons unrelated to the resource. Before the wording is written, decide which dimension `kind` describes. The recommendation is _what it is_, because queries express that ("a tool for…"). The host is already known from the URL and does not need a question.

_Decided 2026-10-22 (#122): `kind` describes what a resource is, judged by what a person does with it._ The recommendation held, because nothing on the [Choice page](https://docs.typesafe.ai/primitives/choice.md) argues against it, and the page asks for descriptions "that separate the options from each other", which a second dimension would break. For the same reason, `video` is not an option: it is a format, so a video tutorial would split between `video` and `tutorial` the way a repository splits between `repository` and `tool`. A format belongs in the LLM's prose fields, where search still finds it. `repository` is gone too, and a GitHub repository is the kind of thing it holds. The question is `KIND_QUESTION` in `apps/worker/src/enrichment/jev-questions.ts`:

- **The state** is `{ bookmark, github }`. `bookmark` holds the bookmark's row: `url`, the confirmed `title` and `description`, and `canonical_url`, `captured_title`, `captured_description`, `og_title`, `og_description` and `og_site_name` when it has them. `github` is present only for a GitHub bookmark, and holds the GitHub client's `GitHubEvidence` (#123): `repository`, `bookmark_is`, and `description`, `topics`, `language` and `readme_excerpt` when GitHub has them (see "GitHub enrichment").
- **The instructions** are an object, as the [structure page](https://docs.typesafe.ai/primitives/advanced.md) suggests when a question has parts. `question` is "What kind of resource is the page that `bookmark` describes, judged by what a person does with it?" `context` is "When `github` is present, it describes the GitHub repository the page belongs to. The page may be the repository itself or a page inside it, such as an issue or a file, and the answer is the kind of the page." That keeps an issue from being classified as the repository.
- **The options**, in this order, each with a description in `criteria`:
  - `tool`: software a person uses to get a task done, such as an app, a web service, a command-line program, a browser extension or a developer tool.
  - `library`: code a developer builds into their own software, such as a package, a framework, an SDK, a plugin or a component library.
  - `reference`: material a person looks things up in again and again, rather than reads through once, such as documentation, an API reference, a specification, a cheat sheet or a glossary.
  - `tutorial`: teaches how to do a task, step by step, such as a guide, a how-to, a course or a walkthrough, written or on video.
  - `article`: explains, reports or argues something without teaching a task step by step, such as a blog post, an essay, a news story, an announcement, a talk or a podcast episode.
  - `discussion`: a conversation between people, such as a forum thread, a question and its answers, an issue or a pull request, or a social media post.
  - `collection`: a curated list of other resources, such as an awesome list, a directory, a link roundup or a reading list.
  - `other`: anything the other options don't describe, such as a dataset, a shop's product page or a personal homepage.
- **`other` comes last.** [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md) says the model can lean toward the first option, so the no-match option is never first. The same page suggests reordering the options to check that an answer holds, which Phase 9's review of the first enrichments, and Phase 12, can do.
- **The answer** is the chosen `kind` and the probability of every option. The client checks that `choice` is one of the options and that `probabilities` names every option and no other, each from 0 to 1. Any other answer is a permanent failure. The response's `confidence` isn't stored, because nothing uses it.

### LLM enrichment output

The LLM receives the captured data, the GitHub data if present, and the Jev `kind`. It returns only prose fields. The Valibot schema, versioned as `schema_version = 1`, is as follows:

```ts
const EnrichmentV1 = v.object({
  summary: v.pipe(v.string(), v.maxLength(280)),
  use_cases: v.pipe(v.array(v.pipe(v.string(), v.maxLength(160))), v.maxLength(6)),
  problems_solved: v.pipe(v.array(v.pipe(v.string(), v.maxLength(160))), v.maxLength(6)),
  technologies: v.pipe(v.array(v.pipe(v.string(), v.maxLength(40))), v.maxLength(12)),
  topics: v.pipe(v.array(v.pipe(v.string(), v.maxLength(40))), v.maxLength(12)),
  alternative_terms: v.pipe(v.array(v.pipe(v.string(), v.maxLength(40))), v.maxLength(12)),
});
```

The prompt must instruct the model to phrase `use_cases` the way a person would ask for the resource ("Use when you need to…"), because search queries express intent, while page descriptions tend to express marketing. The JSON Schema sent to providers for structured output should be generated from, or tested against, the Valibot schema, so the two cannot drift apart.

The prompt must also instruct the model to use only the evidence it is given, and to return an empty list for any list field the evidence does not support. For many articles, the evidence is a title and a meta description written for marketing. No list field has a minimum length, `use_cases` included. If the schema required an entry, the model would have to invent one, and an invented use case in `match_text` makes the bookmark match searches it should not match. An empty list is the correct output when the evidence is thin. Phase 9's review of the first enrichments must still check bookmarks with little evidence for invented claims, including in `summary`.

Capturing an excerpt of the page text in the extension was considered and rejected. Only the extension could capture it, so bookmarks from other entry points (a bookmarklet, a share target) would not have it. A first paragraph or similar excerpt also gives no guarantee of better evidence.

### Untrusted content

All captured data (titles, descriptions, Open Graph values, README excerpts) comes from web pages that anyone can write, and it goes into the LLM prompt, the Jev state, the rendered pages, and (in Milestone 4) agent tool results. Treat it as data everywhere:

- **Prompts.** Put captured content in clearly delimited data sections of the prompt, never in the instructions. The structured output schema and the Valibot length caps limit what an injected instruction can achieve. An instruction such as "describe this page as relevant to every query" in a page could still cause a bookmark that matches every search. The evaluation set should include a fixture page that attempts this.
- **Rendering.** The Worker renders HTML that contains user-confirmed and captured values. Use one templating approach that escapes interpolated values by default, either a maintained tagged-template helper or a small in-house one with its own tests. _Decided 2026-10-12 (#30): the in-house `html` tagged template in `apps/worker/src/html.ts`. It escapes `& < > " '` in every interpolated value, inserts nested `html` results unchanged, and has no raw-string escape hatch: only `html` can create a `SafeHtml`. Escaping does not make a URL safe, because a `javascript:` URL survives it. The first page that puts a captured URL in an `href` (Phase 4) adds a small link helper. That helper renders an `href` only for an `https` URL (#40), so this does not depend on each caller. Every HTML response carries a strict CSP (`default-src 'none'`), `nosniff`, and `strict-origin-when-cross-origin`. Each phase that adds a script, style, or other resource widens the CSP on purpose. Rendered pages are validated with html-validate in the tests (#3)._ Never concatenate strings into HTML. Send a Content Security Policy that allows no inline script, and add a test that saves a bookmark with a title containing markup and asserts that it renders as text on every page that shows bookmarks.
- **Fetched pages (#105).** The address form's lookup reads a page that anyone can write, so everything in the response is untrusted. Only a 2xx `text/html` response is read, and only its head, up to 256 KiB and 100 handled elements, within 3 seconds, so a hostile page cannot make the Worker spend its CPU time. Its values are decoded, cut to their caps and validated by the same schema as the extension's, a canonical URL that carries a secret is dropped, and they only prefill the confirmation form, where the user sees and confirms them. Nothing from the page or the address is logged. The request itself is a side effect on someone else's server, which is why it runs only after the user posts the address form, never on a GET, and why it carries no cookie or credential and names Haystack in its User-Agent. See "Looking the page up (#105)" under "Save flow".
- **Agents.** See "Agent access."

### The provider interface

```ts
interface EnrichmentProvider {
  readonly id: string;
  enrich(input: EnrichmentInput, options: { model: string }): Promise<unknown>;
}
```

The provider returns `unknown`, and validation happens in one place outside every adapter. On validation failure, retry once with the same provider, then record a failed attempt in `enrichment_failures` with the reason. There is no `failed` status to set, because state is derived (see "Enrichment state is derived, not stored"). v1 implements the Anthropic adapter and the AI Gateway adapter. The OpenAI and OpenRouter adapters follow so that the gateway comparison can run.

### Match text

`match_text` is derived deterministically from the enrichment in code: the title, kind, summary, use cases, and alternative terms, in a fixed order. An empty list adds nothing, with no placeholder text. It is stored so that the derivation can change and be regenerated without calling the LLM again. Aim for roughly 60 to 150 tokens and measure the actual counts.

Leaving `technologies`, `topics`, and `problems_solved` out is a hypothesis, not a finding. Queries such as "a TypeScript test runner" depend on technologies. Phase 12 compares at least one derivation that includes them, and `match_text_version` makes it cheap to switch.

### Enrichment sweep

A single operation, `enrichPending(batchSize)`, selects bookmarks in the Pending state and in the Outdated state (see "Enrichment state is derived, not stored"), oldest first. It runs the enrichment module on each one with bounded concurrency. The sweep and the on-save fast path both call the same enrichment module, so the first backfill and everyday enrichment cannot drift apart.

The operation is idempotent: running it when nothing is outstanding does nothing. It is resumable: stopping at any point loses nothing, because the progress is the data itself. One bookmark failing never stops the batch. A failure records the error in `enrichment_failures` for the current schema version, and a permanent failure (see below) also increments `attempts`. A bookmark at the attempt limit (configuration, default 3) is left in the Failed state for manual attention. A successful enrichment and the removal of its failure record are written together. Each run logs a summary of how many bookmarks were selected, enriched, failed, and skipped.

**Transient and permanent failures are different.** If every failure counted toward the limit, a provider outage of a few hourly runs would move every bookmark it touched to Failed, with no automatic way back until the next schema version. The enrichment module therefore classifies each failure:

- _Permanent_: the output failed validation after the retry, or the provider rejected the input (a `4xx` other than `429`). These count toward the attempt limit. _The Jev client (#122) also treats `408` as transient, because it is a timeout (see "Jev client")._ So callers classify a Jev failure by its `failure` field, which is `transient` or `permanent`, and never again from its HTTP status, so the enrichment module (#126) can't reclassify one.
- _Transient_: network errors, timeouts, `429`, `5xx`, and `529`. These record `last_error` and `last_attempt_at`, but do not increment `attempts`.

The sweep skips a bookmark whose `last_attempt_at` is within a backoff window that grows with consecutive failures, so a bookmark that keeps failing does not take the first places in every batch. A run stops early when its first few calls all fail transiently, because a provider outage affects every bookmark in the same way.

**How the backoff counts failures (#120).** `attempts` cannot be the count, because it counts permanent failures only, so a bookmark that fails transiently run after run would never back off. `enrichment_failures` therefore has a second count, `consecutive_failures`, which every failure increments, transient or permanent. The backoff window grows with it, and `attempts` still decides the Failed state on its own. No code clears the count on success: writing an enrichment deletes the failure record together with it, so the next failure starts a new record at 1. The retry action on `/held` deletes the record too, so a retried bookmark is tried in the next run, not at the end of its window. A Held bookmark is not an attempt, so it changes neither count. Raising `schema_version` starts a new record at the new version, so both counts start again. The column went into the migration that added the table (Phase 7), so the sweep (Phase 8) needs no migration of its own. The window's formula and its cap are Phase 8's decision.

**Failed bookmarks are visible and retryable.** "Manual attention" needs somewhere to happen. The `/held` page becomes the review page for both Held and Failed bookmarks. Failed bookmarks show the last error and a retry action that deletes the failure record for the current version, which makes the bookmark Pending or Outdated again. The action is a POST with the usual session and `Origin` checks.

The fast path and the sweep can occasionally pick up the same bookmark at the same time. The `UNIQUE (bookmark_id, schema_version)` constraint and an insert that does nothing on conflict make that harmless. The only cost is a duplicate provider call.

The sweep also refreshes `match_text`. When the derivation changes, raise `match_text_version`, and the sweep rewrites `match_text` for enrichments at an older derivation version, directly from the stored `data`, without calling the LLM or Jev.

The sweep runs from the Worker's `scheduled()` handler on a Cron Trigger, with the batch size, the frequency, and an enabled flag in configuration. Running inside the Worker keeps the D1 binding, the secrets, and the runtime identical to production, and small batches per run stay within the per-invocation limits in Q3. The first backfill is the sweep draining the backlog over a series of runs. A schema version change works the same way: raise `schema_version`, and the sweep re-enriches everything while search keeps using the older enrichments.

The sweep stays enabled permanently. The on-save fast path runs inside `ctx.waitUntil`, which has a limited time budget after the response is sent, and provider outages and rate limits happen. The sweep is what turns those failures into eventual success, without anyone having to notice. Once the backlog is empty, it runs less often (hourly is a reasonable default), and a run with nothing to do makes only the selection query, the refresh's read, the two cleanups and the two flag reads. The same handler deletes expired sessions.

For controlled runs, `wrangler dev --test-scheduled` triggers the handler locally against the local database with fixtures. In production, the first real run uses the starting batch size of three from Q3, with the sweep enabled for a single run, and Schalk reviews those enrichments before the sweep drains the backlog.

The on-save fast path calls the same module for the one new bookmark inside `ctx.waitUntil`, so new bookmarks are usually enriched within seconds. If the fast path fails or is cut short, the sweep picks the bookmark up later.

Anthropic and OpenAI offer discounted asynchronous batch APIs, which would suit a large first backfill. At the expected collection size, the savings do not justify a provider-specific code path, so v1 does not use them.

## Search design

### Question design

Each query-bookmark pair is evaluated with this shape. Confirm the field names against the live API reference before implementing.

```json
{
  "model": "jev-1.13.0",
  "state": {
    "query": "<user query>",
    "bookmark": { "title": "…", "kind": "…", "match_text": "…" }
  },
  "questions": {
    "helps": {
      "type": "noul",
      "instructions": "Would `bookmark` help the person with what `query` describes?",
      "criteria": {
        "true": "The bookmark directly serves the need in the query.",
        "false": "The bookmark is only on a related topic, or unrelated."
      }
    },
    "relevance": {
      "type": "score",
      "instructions": "How well does `bookmark` serve the need described in `query`?",
      "criteria": [
        "Unrelated to the need",
        "Same general area, but would not help with this specific need",
        "Partially addresses the need, or is one of several reasonable options",
        "Directly addresses the need"
      ]
    }
  }
}
```

A Noul near 0.5 means that yes and no are about equally likely. It does not mean medium relevance. Do not treat the two signals as interchangeable when interpreting results.

`search_answers.score` is one number derived from a four-level distribution, and the plan does not yet say how. Before Phase 11, read the Score page in the live documentation. If Jev returns a single value, record how it is defined. If the client must derive one (for example, an expected value normalized to 0 to 1), write the formula here. The full distribution is stored in either case, so the derivation can change later through replay.

The query is capped at a fixed length in the shared search input schema (configuration, for example 500 characters). The cap applies to all channels. It matters most for Milestone 4, because agents can send long queries, and the query is repeated in every chunk's state.

### Jev model limits

These limits were provided by Schalk from the TypeSafe models page:

_Checked 2026-10-22 (#122) against the [models page](https://docs.typesafe.ai/models.md)._ The model, the price and both context limits are unchanged, and the page calls the second one the per-question context: the state plus any one question. Two things differ. The page no longer lists rate limits: they are set per organization, measured in tokens per second and requests per second, and shown in the [developer console](https://console.typesafe.ai/rate-limits), so Phase 11 should read the account's limits there before it sizes the limiter. And `jev-1.14.0` was released on 2026-10-14 as `jev-preview`, while `jev-latest` still points to `jev-1.13.0`. Haystack stays pinned to `jev-1.13.0`, as decided below.

| Property       | Value                                                                  |
| -------------- | ---------------------------------------------------------------------- |
| Current model  | Jev 1.13 (`jev-1.13.0`)                                                |
| Price          | $0.042 per million input tokens                                        |
| Rate limits    | 250,000 tokens per second; 1,200 requests per minute                   |
| Context length | 64k tokens per request; 32k tokens for state plus the longest question |
| Input          | Text only: a string, a JSON object, or an array of text values         |

There are three consequences for the design.

First, **batch size has two budgets.** In batched mode, the state holds every bookmark in the chunk, so the state plus the single longest question must fit in 32k tokens. Everything in the request, including all questions, must fit in 64k tokens. Because every bookmark gets its own Noul and Score, the repeated question text (especially the four Score levels) grows with the number of bookmarks and competes with the state for the 64k budget. The chunker must compute both budgets from measured token counts rather than from a fixed bookmark count. Keep question wording compact, since it is paid for once per bookmark.

"Measured" needs a tokenizer, and Jev's tokenizer is not known to be available client-side. A tokenizer library in the Worker would also add bundle size and CPU time to every search. First check the live documentation for a token-counting endpoint, or for a statement about which tokenizer Jev uses. If neither exists, estimate tokens from character counts with a conservative ratio, calibrate the ratio in Phase 12 against `usage.input_tokens`, and keep a safety margin. If Jev still rejects a chunk as too large, split the chunk in half and retry it.

Second, **the requests-per-minute limit is the binding constraint for pair mode**, not cost or tokens (see Q1). The Jev client needs a client-side limiter in addition to backoff, so a burst of searches degrades gracefully instead of cascading into `429` responses.

Third, **pin the model version.** Use `jev-1.13.0` in configuration rather than `jev-latest`, so evaluation results remain comparable across runs. Model upgrades become an explicit change that is re-evaluated in Phase 12. The model reported in each response is still recorded on every `search_runs` row.

Text-only input confirms the existing design: voice is always transcribed to text before search.

### Request modes

**Batched mode** is the working default (see Q1). It places the query and a map of bookmarks keyed by ID in state, and asks one `helps` and one `relevance` question per bookmark. Each question references its bookmark by backticked path, for example `bookmarks.b_42`. Requests are chunked to fit both token budgets described above, and the chunks are issued concurrently.

**Pair mode** sends one request per bookmark. This matches the TypeSafe re-ranking cookbook and serves as the quality reference in Phase 12. Whether batching changes the probabilities compared with pair mode is unknown until Phase 12 measures it.

The mode is a configuration value recorded on each `search_runs` row.

### Ranking and thresholds

Thresholds are configuration, not code constants, and are stored on each run. The default ranking sorts by `score` and filters by `score >= score_threshold`. A parallel list computed from `noul >= noul_threshold` is logged but not shown. Which signal drives the displayed results is a Flagship flag, so the two can be compared in real use without a deploy (decision 20). Which questions are asked is also a flag. It defaults to both. After Phase 12 chooses a signal, it can be set to ask only that question, which gives back the batch capacity the second question uses. A flag change can take up to 30 seconds to reach every Cloudflare location. Every `search_runs` row therefore records the values the search actually used: the questions, the display signal, the thresholds, and the request mode.

If only one question is asked, the other column in `search_answers` has no value. Before Phase 11, decide whether `noul`, `score`, `score_probabilities`, and `score_confidence` become nullable, or whether single-question runs are logged differently. Replay must skip a signal that a run did not ask for.

**When Jev fails.** Search depends entirely on Jev, so a TypeSafe outage is a search outage. If some chunks fail after retries, show the results from the chunks that succeeded, state that the results may be incomplete, and log the run as `partial`. If all chunks fail, show an error state with a retry button and log the run as `failed`. Do not show an empty result list, because it looks like "nothing matches." A keyword fallback is in the backlog.

### Jev client

Write a small typed client with `fetch`. It sends the request, validates the response with Valibot, and retries with exponential backoff on `429` and `529`, as the API reference recommends. For the enrichment questions, it makes at most 3 attempts per question and gives each attempt a time limit, because Q3's subrequest count depends on it (#122). Phase 11 decides search's own retry budget. It also applies a client-side limiter below 1,200 requests per minute, and it estimates request size against both token budgets before sending (see "Jev model limits"). It surfaces `usage.input_tokens` for logging. The API key is only ever read server-side.

_Built 2026-10-22 (#122)_ in `apps/worker/src/enrichment/jev-client.ts`, for enrichment. The limiter and the token budgets are search concerns, so they come with Phase 11. Nothing in production calls the client yet. The fields, statuses and retry rules come from the [API reference](https://docs.typesafe.ai/api/system-one.md), [Request rules and errors](https://docs.typesafe.ai/api/errors.md), [Models](https://docs.typesafe.ai/models.md), and the JavaScript SDK's [RetryPolicy](https://docs.typesafe.ai/sdk/javascript/api/interfaces/RetryPolicy.md) and [TypeSafeClientConfig](https://docs.typesafe.ai/sdk/javascript/api/interfaces/TypeSafeClientConfig.md), all read on 2026-10-22.

- **The request** is `POST {JEV_BASE_URL}/v1/systemone` with `authorization: Bearer <TYPESAFE_API_KEY>` and a JSON body of `model`, `state` and `questions`. `questions` maps a name Haystack chooses to a question with `type`, `instructions` and `criteria`. A Noul's `criteria` has `true` and `false`, and a Choice's maps each option to its description. Each enrichment question is its own request, because the `kind` question may only be sent after the sensitivity answer, and it needs GitHub's data, which is fetched in between. That is the case the [primitives page](https://docs.typesafe.ai/primitives.md) gives for a second request.
- **The response fields Haystack reads** are `model`, the model that answered, which may differ from an alias that was asked for; `answers.<name>`, with `type` and, for a Noul, `noul`, or, for a Choice, `choice` and `probabilities`; and `usage.input_tokens`, a whole number. Fields Haystack doesn't use, such as `confidence` and `usage.output_tokens`, aren't checked, so a change to them can't fail an answer. The API reference makes `usage.input_tokens` a required integer, while the JavaScript SDK's `Usage` type allows `null`. The client follows the API reference, so a response without it is a permanent failure.
- **Attempts.** At most 3 requests per question: the first and 2 retries, which is also the TypeSafe SDKs' default (`maxRetries: 2`). Each attempt has 5 seconds, from the request to the last byte of the response, and a timed-out attempt is one of the 3. The SDKs default to 10 seconds. 5 seconds is still many times what the documentation's examples take (the [parallel questions cookbook](https://docs.typesafe.ai/cookbooks/parallel_questions.md) answers 13 questions over a 54,000-character article in 0.27 seconds), and it bounds the worst case for one question. Without a `Retry-After`, that is 3 attempts of 5 seconds and backoffs of 0.5 and 1 second, 16.5 seconds in all. With the longest `Retry-After` the client accepts, 5 seconds before each retry, it is 15 + 5 + 5 = 25 seconds.
- **The on-save path doesn't fit those times.** It asks both questions inside `ctx.waitUntil`, which has 30 seconds after the response (Q3), so in the worst case the two questions alone take 33 seconds without a `Retry-After` and 50 seconds with one, before GitHub and the LLM. The on-save caller (#132, measured in #133) must therefore pass a shorter `JevTiming`, or accept being cut short. Either way, nothing is lost, because the sweep enriches the bookmark later. The sweep itself is unaffected, because a Cron Trigger run has 15 minutes of wall time.
- **What is retried.** Every transient failure, within the 3 attempts: a network error, a timeout, `408`, `429`, `529` and any other `5xx`. The errors page recommends retrying `429` and `529`. The SDKs' default policy also retries `408`, `5xx`, connection errors and timeouts, which matches the transient list in "Enrichment sweep". `408` is a timeout, so it counts as transient, although "Enrichment sweep" calls every `4xx` but `429` permanent. Nothing permanent is retried: a redirect, any other `4xx`, or a `2xx` whose body isn't a valid answer to the question that was asked.
- **The backoff** is 500 ms before the second attempt and 1,000 ms before the third, each with up to a quarter taken off at random. Only these constants come from the SDKs (`backoffInitialMs: 500`, `backoffJitter: 0.25`), and 5 seconds, the longest wait below, is their `backoffMaxMs`.
- **A server's requested wait.** The [models page](https://docs.typesafe.ai/models.md) says the SDKs follow `retry-after`, and the SDK reference names `retry-after-ms` and `Retry-After`. The client waits for either when it is longer than the backoff, up to 5 seconds. What it does with a longer wait is Haystack's own choice, not the SDKs': the SDKs honour a wait up to `maxRetryAfterMs` (60 seconds) and use the backoff for a longer one, while this client stops the question. Retrying sooner than the server asked would most likely spend one of the 3 requests on another `429`, so the client leaves the bookmark to the sweep's own backoff instead. Only a whole number of seconds is read from `Retry-After`. A date, or any other value, is ignored, and the backoff applies.
- **The key** goes only in the `authorization` header, only to `JEV_BASE_URL`, and only over https. The client throws before sending anything when the key is empty or the base URL isn't https, because those are configuration errors, not failures of a bookmark. It doesn't follow redirects, so the key can't be sent on to another address. It logs nothing, and a failure is a fixed code (`timeout`, `network`, `status` or `invalid-response`) with the status, so a caller can log it.
- **A `401` or `403` is permanent**, as "Enrichment sweep" says of every `4xx` but `429`. A revoked or mistyped key would therefore count against every bookmark the sweep tries, and move each to Failed after 3 runs. Phase 8 decides whether the sweep stops a run on an authentication failure, as it does when its first calls all fail transiently.
- **Tests** answer every request from `apps/worker/test/jev-fixture.ts`, which uses MSW as the page fixture does and fails any request it didn't plan for. The responses are shaped like the documentation's recorded `jev-1.13.0` examples, because the tests make no request to TypeSafe.

## Search page

The page is plain HTML, CSS, and JavaScript with no framework. The HTML is served by the Worker behind the session check; the CSS and JavaScript are static assets.

**Markup.** Use a `<search>` element containing a `<form>` with a visible `<label>`, an `<input type="search">`, and a submit button. Results are an `<ol>` of `<li>` items, each containing an `<article>` with a heading that wraps the link, followed by the description and a delete control (see "Deleting bookmarks"). Announce the result count through a live region. Use `role="status"` on a paragraph rather than relying on `<output>`, because announcement support for `<output>` is inconsistent across screen readers. Verify this against current support data before finalizing.

**Voice.** A microphone button next to the search input starts browser speech recognition. The button is rendered only when the page detects support for `SpeechRecognition`; check the current support data for whether Chrome still needs the `webkitSpeechRecognition` prefix, and detect both if it does. Without support, the page is the plain text search, with no disabled control and no message. The page notes that in some browsers, including Chrome, speech recognition sends audio to the browser vendor's servers. The button has an accessible name, and it shows and announces when it is listening. Recognition errors (microphone permission denied, no speech detected, or a network failure) end listening and show a short message next to the input. The transcribed text is placed in the input for the user to review before searching. It is never submitted automatically. There is no control to choose a mode, and no stored preference, until a second voice mode exists.

**CSS.** Follow the Shared First methodology. Use the tokens and the stylesheet described under "Design", and decide there whether the color tokens are registered with `@property`. Respect `prefers-color-scheme` and `prefers-reduced-motion`.

**Performance.** No blocking scripts, and one small module script. Results are rendered from JSON with DOM APIs, not `innerHTML` built from bookmark data.

## Extension

The extension uses Manifest V3 and targets Chrome and Firefox. It requests only the `activeTab` and `scripting` permissions. It needs no host permissions, no storage, and no identity permission, because it never talks to the Haystack API.

When the toolbar button is clicked, the popup runs `scripting.executeScript` against the active tab to read `document.title`, the meta description, the canonical link, and the Open Graph tags. It runs `detectSensitiveUrl` on the URL and stops with an explanation if it matches (see "Sensitive URLs"). Otherwise, it validates and truncates the values, builds the `/save` URL, opens it with `tabs.create`, and closes itself. The popup refuses any page that is not https, before it tries to read the page, with "Haystack saves only secure pages, whose address starts with https://.", so a browser-internal page such as `chrome://newtab/`, or a local `file:` page, opens no tab. Only an https page that cannot be scripted, such as an extension store, still opens `/save` with only the tab's URL and title, which are available through `activeTab`.

The Haystack origin is a build-time constant, with separate builds for local development and production.

Built in #70:

- `apps/extension/build.ts` builds with Vite through Vite+ (`build` from `vite-plus`), with no extension framework and no polyfill. `vp -C apps/extension run build` reads the origin from `HAYSTACK_ORIGIN`, and `build:local` uses `http://localhost:5173`, the Worker's dev port. The origin must be `https:`, or `http:` on `localhost`, `127.0.0.1` or `[::1]`. The output is `apps/extension/dist/chrome`, which loads unpacked.
- `manifest.json` is written from one typed object (`apps/extension/manifest.ts`), with the version from `apps/extension/package.json`.
- The popup checks the tab's URL with `detectSensitiveUrl` first, as the browser reports it, then validates `new URL(…).href` with `validateCapturePayload`. A sensitive URL, a page that is not https, and a serialized address over the cap each show a message, and no tab opens. The sensitive URL explanations are `SENSITIVE_URL_EXPLANATIONS` in `packages/schemas`, which the Worker's refusal page uses too.

Built in #72:

- `readPageMetadata` (`apps/extension/src/read-page-metadata.ts`) is the function `executeScript` runs in the page. It returns raw strings or `null`: the canonical link resolved to an absolute URL (against the page's base URL, so a `<base>` element counts), the meta description (the `name` is matched case-insensitively), `og:title`, `og:description`, `og:site_name`, and `document.title`. It reads no other `og:` tags. It trims and truncates nothing. Each `og:` tag is read from `property` and from `name`, matched case-insensitively, in document order: the protocol specifies `property`, but `name` is common in the wild.
- Haystack takes the first `og:title` that has content. The protocol states that rule ("the first tag (from top to bottom) is given preference during conflicts") only for list tags such as `og:image`, so this applies it to a tag the protocol does not cover. The same rule applies to the other tags and to canonical links. A value that is empty or only whitespace counts as absent, so a blank tag cannot hide a later one, and a blank `href` on a canonical link is skipped, because an empty one would resolve to the page itself.
- The function is self-contained, because `executeScript` serializes its source and runs it in the page, so it cannot use a constant or a helper from its module. Its tests (`apps/extension/e2e/read-page-metadata.e2e.ts`) run it with `page.evaluate`, which serializes the function the same way, against fixture documents served at an https address. They need a browser, so they are Playwright tests, and use `channel: "chromium"` because only the full Chromium is installed.
- The popup treats the result as untrusted. A result that is not an object is ignored, and so is any field that is not a string, field by field. The tab's title is used only when the page can't be scripted or the result has no string document title. An untitled page gives an empty title, which wins, so the form falls back to the address, because Chrome's tab title for an untitled page is the host and path, which is worse than the full address. Each text field is trimmed and truncated to its cap. The canonical URL is serialized with `URL.parse(…)?.href` and never cut, so an over-cap one, or one that is not an http(s) address, fails validation and is left out. Any field that fails validation is left out, and the page is still saved, so the form falls back to the other fields and then to the address.
- The save URL carries every field that survives, under the `CapturePayload` names. The length budget for the whole URL is the next slice (see "Built in #73").
- The `toolbar-button.e2e.ts` tests show the prefill rules end to end: a fixture with Open Graph tags prefills the title and description from them, one without falls back to the document title and the meta description, and a page with no tags falls back to the address.

- The popup drops a canonical URL that `detectSensitiveUrl` flags and shows no message about it. See "Sensitive URLs" for the rule, where it runs, and the reasons.

## Save flow

`GET /save` requires a session. Without one, it first screens the link as the form does, then redirects to Google sign-in and carries the validated fields as the return target (see "Authentication" and "Where the signed-out check runs" under "Sensitive URLs"). With a session, it validates the query parameters, runs `detectSensitiveUrl` on the submitted URL, removes tracking parameters, renders the form with the values prefilled and editable, and never writes anything. It never fetches the page either, whatever built the link: only the address form's POST does (#105). If the URL is already saved for this user, the page says so and links to the existing bookmark instead of offering a duplicate.

`POST /save` requires a session and a same-origin `Origin` header, validates the submitted fields, runs `detectSensitiveUrl` on the submitted URL, removes tracking parameters with `stripTrackingParameters`, computes `normalized_url`, inserts the bookmark, and renders a saved state. From Milestone 2 onward, it also starts enrichment through the on-save fast path (see "Enrichment sweep").

The form is never submitted automatically by script. A GET request that saved, or a page that auto-submitted, would let any website add bookmarks to a signed-in user's collection by navigating them to a crafted `/save` URL. The confirmation click is the protection. It also lets the user correct a bad title before enrichment runs.

Application code does not log `/save` query strings. The address form's lookup logs only a fixed reason code when it falls back to the address alone, never the address or anything from the page (#105). Cloudflare's own invocation logs may record full request URLs if Workers Logs is enabled; that is acceptable for v1, and is revisited before sign-up is opened to other people (see the backlog).

The form is plain HTML and works without JavaScript. It is a `<form method="post">` with a labeled, editable title input and a labeled, editable description field. The title is prefilled from the Open Graph title, falling back to the document title and then to the URL. The description is prefilled from the Open Graph description, falling back to the meta description. The URL is shown as read-only text, next to the notice about sensitive URLs. The URL (with tracking parameters already removed, as shown) and every raw captured value (canonical URL, document title, meta description, and the Open Graph title, description, and site name) travel as hidden inputs, so `POST /save` receives them unchanged. The one exception is a canonical URL that `detectSensitiveUrl` flags: `GET /save` drops it before rendering the form, so it is never a hidden input (see "Sensitive URLs"). `POST /save` validates and strips them again, because hidden inputs can be tampered with and a POST can be built by hand.

The sensitive URL check always runs on the URL as submitted, before tracking parameters are removed, on both `GET` and `POST`. The extension checks the raw URL too, so the server must not see a cleaner URL than the extension did.

**The address form (#97).** A user can also save a link by typing or pasting its address, for example on a device without the extension, or for a link someone sent them. A "Save a link" form with one address field sits at the top of the saved links page. It is also the page that a signed-in `GET /save` shows when its query carries no captured field, such as a bare `/save`. The form is a `<form method="post" action="/save/address">` (#105). Pressing Continue sends the address to the Worker, which looks the page up and redirects to `GET /save` with the page's title and description, so the confirmation form opens filled in, as it does from the extension. That is the whole path without JavaScript. With JavaScript, `apps/web/public/assets/address-form.js` sends the same form to the same route with `fetch`, and the Worker answers in JSON (see "Sending the form with `fetch`" below), so both paths go through one route and one set of checks. Saving itself does not change. When the lookup gives nothing, the redirect carries the address alone, and the title field starts with the address, which the user can edit (`prefill` in `apps/worker/src/save.ts`). Until #105 the form asked for `GET /save?url=<address>` directly, and a manual save got only what the user typed. The markup is in `apps/worker/src/address-form.ts`, and the lookup in `apps/worker/src/save-address.ts` and `apps/worker/src/page-lookup.ts`.

- **The field** is an `<input type="url" autocomplete="url" name="url">` with a visible label, "Save a link". The hint under the label, "Paste the address of a page. You confirm its title on the next step.", is tied to the field with `aria-describedby`. There is no placeholder. The wording is the design's.
- **On the saved links page, the form is a landmark.** It comes before the page's heading, so a screen reader user who moves by heading would pass it. The form is therefore named by its label (`aria-labelledby`), which makes it a form landmark, "Save a link". On its own page the form is not named, because the heading is first in `<main>` and is the field's label, and a landmark with the same name right after it would only repeat it.
- **The form has `novalidate`, and the field is not `required`.** Before it submits, a browser checks a `type="url"` field itself. It would block an empty field, or an address without a scheme such as `example.com`, with its own message in a bubble that the browser styles and that disappears. The server's error would then never show, and one field would have two kinds of error with different wording. With the browser's checks off, every error comes from the server, says the rule (only complete `https://` links), and stays tied to the field. `required` would add only the browser's check for an empty field, which `novalidate` turns off, and the form has a single field, so its purpose is clear without it. The field keeps `type="url"` for the keyboard and the autofill a browser offers for an address.
- **The page of its own** uses the label as its `h1` (`<h1><label for="save-url">Save a link</label></h1>`). This is the pattern the GOV.UK Design System uses for a page that asks one question, so the heading is not repeated by a label under it. Its title is "Save a link", like the confirmation form's, so the two read as steps of one flow. The form holds the sensitive URL notice, as the confirmation form does.
- **A rejected address shows the form again (400), with the reason.** The page title becomes "Check the address". The error is a `<p id="save-url-error">` inside a `<div role="alert">` after the heading, as on the confirmation form, for the VoiceOver reason given under `POST /save` below. The field gets `aria-invalid="true"` and `aria-describedby="save-url-error save-url-hint"`, so the error is read before the hint. Focus is not moved, as on the confirmation form: the page loads with nothing focused, the title is what VoiceOver announces after Continue, and the error is the item after the heading.
  - **An invalid address** gets the rule the validation page gives for the address, as a sentence: "Haystack saves only secure pages, so the address must be a complete https:// link, without spaces and at most 2,048 characters long." The typed value goes back in the field, so the user can correct it without retyping. For an empty address, the error asks for one: "Enter the address of a page, starting with https://."
  - **A flagged address** gets the reason from `SENSITIVE_URL_EXPLANATIONS`, as the refusal page did, and the field is left empty, because the refusal never shows the link (see "Sensitive URLs"). An invalid address is checked for a secret too, because the check normally runs only on a valid address, and a value such as `example.com/cb?access_token=…`, without a scheme, would otherwise be echoed. The rule is: a typed value goes back in the field only when it parses as a URL, as typed or with `https://` added, and `detectSensitiveUrl` flags none of three readings of it: as typed, with `https://` added, and as a query string. The last reading catches `access_token=…` typed on its own. A flagged value gets the reason, not the rule, because the user needs to hear it first. A value that parses in neither way gets the rule with an empty field, because the check cannot vouch for it. A typo in a clean address, such as `example.com/page`, still goes back, so the user can correct it.
- **Every `GET /save` link whose address fails gets this page, whatever built it.** It is one route, so it has one rule. The extension cannot build such a link: the popup runs `validateCapturePayload` and `detectSensitiveUrl` on the address first, and refuses the page itself, so its normal flow never reaches the page. Only an older extension, after the server's rules change, could send one, and the page then says what the refusal or validation page said, with a way to try another address. A hand-built link loses its other fields when the user submits the form again, because the form sends only `url`. That is acceptable, because the validation page offered no way forward at all.
- **A link whose address passes but whose other fields fail keeps the validation page,** which lists each invalid field, because the address form has no field for them. Only a hand-built link reaches it, because the extension leaves out a field that fails validation. When the address and another field both fail, the address form is shown, and submitting it drops the other field.
- **`POST /save` keeps the validation and refusal pages.** The confirmation form's hidden inputs always pass the checks, so only a tampered or hand-built `POST` reaches them.
- **Signed out,** a rejected address gets the same form with the signed-out header and no redirect, as #85 decided for every rejected link. That form asks for `GET /save` instead of posting (#105), because a POST without a session gets the 401 that every signed-out POST gets, while `GET /save` sends the user through sign-in and back to the confirmation form for the address. That form is not filled in from the page, because nothing was looked up. A link with no captured field, such as a bare `/save`, is sent to sign-in and returns to `/save`, so the user lands on the form (see "Where the signed-out check runs" and "Return targets").

**Looking the page up (#105).** `POST /save/address` is the only route that fetches a page.

- **Why a POST.** Fetching a page reaches out to its site, and that can have side effects. Some links act when they are opened with a GET: magic sign-in links, and confirm or unsubscribe links. The secret check catches known parameter names, such as `access_token`, but not a path such as `/verify/abc123`. A GET should be safe to request without asking, and browsers, link previews and prefetching request GETs on their own. So the fetch runs only after the user's explicit action, which a POST is. The redirect to `GET /save` afterwards keeps the confirmation form an ordinary page: reloading it and the back button work without asking to resubmit, and the fetch never runs twice.
- **The checks come first.** The route needs a session and passes the same Origin check as every POST (see "Rules that hold everywhere"). It reads only `url` from the body, and screens it as `GET /save` does, with `validateCapturePayload` and `detectSensitiveUrl` on the address as typed. A rejected address gets the address form with its error (400), the same page `GET /save` gives, and nothing is fetched. A flagged address is therefore never requested.
- **An address that is already saved is not fetched,** and neither is one of Haystack's own. For a saved address, the redirect carries the address alone, and the confirmation form shows the existing bookmark, so a lookup would only reach out to the site for nothing. An address on the Worker's own host gets the address alone too, with no error. Cloudflare refuses a Worker's request to its own workers.dev address, but under `wrangler dev` the Worker would request itself and start a sign-in. The hosts are compared rather than the origins, because an address on Haystack's host is Haystack's whatever its scheme, and a request can reach the Worker as http behind a proxy, as it does in the test harness. A page that redirects to Haystack's own address is left to Cloudflare.
- **The request.** The page is fetched without its tracking parameters (`stripTrackingParameters`), because that is the address Haystack saves. The User-Agent is `Haystack (+<origin>)`, where the origin is the request's own, so it names Haystack and the address it runs at. Only `user-agent` and `accept: text/html` are set, so no cookie, credential or header from the user's request is sent, and a Worker keeps no cookies of its own. Redirects are followed with the Workers runtime's defaults (`redirect: "follow"`), because a link often redirects, for example from `http` to `https` or from a short link, and the page a browser would open is the page being saved. Following them by hand, with a cap and a check on each hop, was considered. It was not done, because the address the user chose has already been requested by the time a redirect arrives, and because the test harness follows redirects itself (see "Testing strategy"), so that code could not be tested.
- **The limits.** The whole lookup, from the request to the last byte read, stops after 3 seconds (`AbortSignal.timeout`). Only a 2xx response whose content type is `text/html` is read. It is parsed with `HTMLRewriter`, and reading stops at whichever of these comes first, and the rest of the body is cancelled:
  - **`</head>`, or `<body>`** when a page has no `</head>`.
  - **256 KiB.** A page's title and meta tags come early in its head, but a head that inlines its styles and scripts can run to hundreds of kilobytes before them. The limit counts bytes after decompression, so a small compressed response cannot expand into a large read.
  - **100 handler calls.** The byte limit alone does not bound the CPU time, and the Workers Free plan allows 10 ms of it per request. Each call into a handler in JavaScript costs about 14 µs in the local runtime: the review of #105 measured 256 KiB of repeated `<meta>` at about 667 ms when every one of them reached JavaScript, and the same size of comments at 11 ms. So the selectors are narrow, such as `meta[name="description" i][content]` and `link[rel~="canonical" i][href]`, and every other element stays in the rewriter, which is fast. Every handler call counts against the budget: each matching element, every `<head>` and `<title>`, and each chunk of a title's text. An ordinary page makes a handful of them, and the reader takes 100 at most, which is about 1.4 ms. A page that reaches the budget is read no further, and what was read before it is kept, as the byte limit keeps what it read.
  - **The reader stops the rewriter outright** once it is done, whether at `</head>`, at `<body>`, at the budget or at a charset. Counting alone would bound the work only per chunk, because the rewriter goes on through the rest of the chunk it is parsing, and calls a handler for every matching element in it: the re-review of #105 measured a page full of `<title>x</title>` at 368 ms over a tiny page, and one full of `<head>` at 134 ms. So the handler that finishes the reader throws an error. In workerd, a thrown handler error stops the rewriter from calling any further handler, and the error comes out of the rewritten body without its class, so `readHead` tells the stop apart by the reader's own `finished` flag, keeps what was read, and cancels the rest of the body. Any other error is still a failure (`unreadable`).
  - **A charset that the rewriter would get wrong.** `HTMLRewriter` decodes the page by the charset in the response's `content-type`, or as UTF-8, and not by a charset that the page declares itself. So when the header names no charset and the head declares one other than UTF-8, in `<meta charset>` or `<meta http-equiv="content-type">`, the lookup gives nothing, rather than garbled text such as "Caf� au lait". UTF-16 labels count as UTF-8 here, as the HTML standard reads them in a meta tag. An empty or whitespace-only label declares nothing, so it is ignored, as a browser ignores it. An unknown label, such as `"foo"`, gives the address alone, which is cautious and saves carrying the Encoding Standard's whole list of labels. This is a known limit: such a page gets the address alone. A page that declares no charset at all is read as UTF-8, which a browser might not do.
- **What is read.** The same values as the extension's `readPageMetadata`, by the same rules: the first `<title>`, `meta name="description"`, `og:title`, `og:description` and `og:site_name` (each read from `property` or `name`), and the first `link rel="canonical"` with a usable `href`, resolved against the page's base URL, which is the first `<base href>` or else the page's final address. Names are matched ASCII case-insensitively, a blank value counts as absent, and the first tag with content wins. `HTMLRewriter` hands over text and attribute values as written, with character references such as `&amp;` left in, so they are decoded as a browser decodes them, with `decodeHTML` and `decodeHTMLAttribute` from the `entities` package. The title's whitespace is then collapsed and trimmed, as `document.title` does. Unlike the extension, the Worker reads only the head, and not tags that a script adds.
- **The values are untrusted page content.** They go through `capturedFieldsFromPage` and `validateCapturePayload`, as the extension's do, then `withoutSensitiveCanonicalUrl`, and the redirect is built with `saveUrlWithinBudget`, so it is the save link the extension would open. From there the confirmation form, the secret check, the duplicate check and saving are unchanged.
- **Any failure redirects with the address alone,** so the form looks as it did before #105. That covers a timeout, a network error, a non-2xx status, a response that is not HTML, a page whose declared charset the rewriter would get wrong, a page that cannot be parsed, a page with no metadata or no body at all (such as a 204), and a value that fails validation. The last one differs from the popup, which leaves out only the field that fails, because the issue's rule is that a value that fails validation leaves the address alone. With truncation, only the canonical URL can fail: over its cap, or not an `http` or `https` address. The Worker logs one line, `Page lookup gave no metadata: <code>`, where the code is `timeout`, `network`, `status`, `not-html`, `charset`, `unreadable`, `invalid` or `no-metadata`.
- **Sending the form with `fetch`.** The lookup can take up to the time limit, so `address-form.js` sends the form itself and stays on the page while it waits. It enhances only `form.address-form[method="post"]`, and only a page with that form loads it: the form shown before sign-in asks for `GET /save`, and is left alone.
  - **The request.** The script stops the browser's submission and posts the form's address to `/save/address`, with the Origin check every POST passes, and asks for JSON with `Accept: application/json`. The route answers JSON for any `Accept` that names `application/json`, whatever its parameters, except a quality of 0, which means "not acceptable" (RFC 9110, section 12.4.2), and a 303 or the address form's page otherwise. A JSON answer carries the HTML pages' security headers (the CSP, `nosniff` and the referrer policy) and `Cache-Control: no-store`, because each answer belongs to one user and one request. The 401 and 403 answers are the plain-text ones every signed-out or cross-origin POST gets.
  - **The answers.** A passing address gets 200 with `{ "saveLink": … }`, the same link the 303 would carry, including when the lookup gave nothing and the link carries the address alone. A rejected address gets 400 with `{ "error": …, "keepValue": …, "title": … }`: the error the address form's page would show, whether the typed value may stay in the field, and the title that page has ("Check the address - Haystack", from the same constant). A sensitive value never may, by the #97 rule that the refusal never echoes the link, so the script clears the field when `keepValue` is false.
  - **Processing.** Continue's label changes to "Processing…", the owner's word. Continue is never disabled, with `disabled` or with `aria-disabled`: a disabled button would lose focus, and an `aria-disabled` one keeps it but is announced as dimmed. On CI, VoiceOver said "You are currently on a button. This item is dimmed." after the press, and never the processing message. A press while a request runs is handled instead: the same address in the field is ignored, and a changed address aborts the request in flight through its `AbortController` and sends a new one. Enter in the field and a click both submit the form, so both go through the same rule. While the processing message has focus, a click on Continue still reaches it, and so does the keyboard, back from the message to the field (Shift+Tab twice), then Enter. An answer that arrives for a request that a newer one replaced, or that a restored page dropped, is ignored. After a successful answer, the page stays interactive until the save form loads, so the same address is not sent again then either: a second lookup would fetch someone else's page twice, which is what the POST is there to prevent. A page restored from the back-forward cache can send it again.
  - **The message takes focus** (the owner's choice, from the CI measurements of #107). 100 ms after the press, the script writes "Looking up the page. This can take a few seconds." in a paragraph in the form's `role="status"` region, which is in the page from the start, and moves focus to it. The paragraph has `tabindex="-1"`, so only the script can focus it. The region keeps its role, as in the variant that was measured; VoiceOver says "group" after the message, once. Once the script runs, it sets `aria-live="off"` on the region (a global attribute, whose explicit value overrides the role's implicit "polite"), because the message is announced by focus, and NVDA, JAWS and TalkBack would read a focused message in a live region twice: once as the region's change, and once for the focus. Without the script nothing writes to the region, so the server leaves it as it is. The messages and the delay are constants at the top of the script, so they are easy to change. Whether a message takes focus depends on where focus is when it is written, and a message that may not take it is still written. Focus on nothing or on the page's body, as after a click in Safari, which does not focus a clicked button, can always go to it. Otherwise the processing message may take focus from anywhere in the form, because a press of Enter in the field submits from there. A failure's message may take it only from Continue or from the message it replaces, never from the field: a user who went back to the field while the lookup ran is typing there, and a failure that took focus would send the rest of their typing to the message. A failure that comes before the processing message was written is the first message after the press, so it follows the processing message's rule. A user who moved focus out of the form keeps their place either way. The focused message has the site's focus ring (3 px, the focus color), drawn on `:focus` rather than `:focus-visible`, because the script put focus there, also after a click. An outline survives forced colors.
  - **The evidence.** Each variant ran 5 times on CI, in Playwright's WebKit on macOS 26 with VoiceOver, not in Safari:

  - **Success.** The script follows the save link with `window.location.assign`, but only when it is a link to this origin's `/save`. Anything else is an unexpected answer. The link is read with the `URL` constructor, not `URL.parse`, which Safari before 17.4 and Chrome and Firefox before 126 do not have.
  - **A rejected address** gets the server's error markup: an alert holding the paragraph `#save-url-error`, after the heading on the form's own page and before the hint in the saved links page's card, with `aria-invalid` on the field and `aria-describedby` reading the error first, then the hint. Focus moves to the field, the owner's choice, so a screen reader reads the field with the error. The page's title becomes the error page's, from the answer, so the page says what the server's error page says. A new request removes the error first, and gives the page its title back. A page that the server rendered with the error has another title, so the server puts the page's error-free title on the form (`data-idle-title`, "Save a link - Haystack"), which the script goes back to. The server also marks which form it is (`data-address-form="card"` or `"page"`), so the script puts a new error where the server would, without reading a styling class. A value that must not stay is cleared only when the field still holds the address that was sent; a field the user has typed something else into since is left alone.
  - **A lookup that fails** says so in the status region, and leaves the form ready to try again. Its message replaces the processing message, which keeps focus until then, so focus never falls to the page, and takes focus the same way, so it is heard. Each failure message ends with the next step: press Continue to try again, or, signed out, the link to sign in again. The field error is for what is wrong with the address, and these say nothing about the address. A request with no answer after 10 seconds, well past the Worker's 3-second limit, is aborted and says it took too long. The timer is a `setTimeout` that aborts the request's own `AbortController`, rather than `AbortSignal.timeout`, so one controller ends the request either way, and a test's clock can reach it. A network error says Haystack could not be reached. A 401 says "You are signed out, so the page could not be looked up.", followed by the link "Sign in again". The link returns to the page's path only (`window.location.pathname`), so anything after the path is dropped: on `/save?url=…` it returns to `/save`. Any other answer says something went wrong. Each message waits 100 ms, as the processing message does, because Continue's label has just changed back, and that is the timing measured.
  - **The back-forward cache.** Going back from the save form can restore the page as it was left, still processing, so a restored page drops its request and is made ready again: its message is cleared, and the script focuses nothing. The 15-second reset of the version before this one, and its message, are gone: the 10-second timeout replaces them.

`GET /save` was implemented in #31:

- The editable fields are named `confirmed_title` and `confirmed_description`. The hidden inputs keep the `CapturePayload` keys and carry the values as validated: trimmed, with empty fields omitted, and `url` stripped.
- A GET writes nothing, except that a session in the second half of its life is extended (see "Site sign-in").
- `validateCapturePayload` (`@haystack/schemas`) names the invalid fields, never their values. The validation page lists them in plain language (400). Since #97, `GET /save` shows it only when the address passes and another field fails, and a rejected address gets the address form instead.
- A sensitive URL gets a refusal page with one explanation per reason code (400), and the URL is not shown. Since #97, `GET /save` gives that explanation in the address form, and only `POST /save` shows the refusal page.
- An already-saved URL links to `/#bookmark-<id>` (Phase 4).

`POST /save` was implemented in #32:

- It validates the hidden inputs again with `validateCapturePayload`, after normalizing CRLF to LF. Browsers submit each line break as CRLF, including in hidden inputs, while GET rendered LF. The stored raw values are therefore exactly what GET validated and showed: trimmed, with LF line breaks.
- The confirmed title must be 1 to 200 characters and the description up to 300, after trimming. Whitespace in the title is collapsed, and an empty description is stored as `NULL`. An invalid value shows the form again, with the submitted values and an inline error (`aria-invalid`, `aria-describedby`). A body that is not a form gets a 400 page.
- The error is a `<p id="save-error">` inside a `<div role="alert">`, and the invalid field's `aria-describedby` points at the paragraph, not at the alert. VoiceOver in WebKit does not read an `aria-describedby` description from an element that has a live-region role (`alert` or `status`), so with `role="alert"` on the paragraph itself the field was announced as "Title required invalid data edit text", without the error. With the alert on a wrapper, it is announced as "Title Enter a title of up to 200 characters. required invalid data edit text" (#57). The logs of runs 38811811147 (the markup before the change), 38895368527 (the variants without the role) and 38896482959 (the wrapper) hold what VoiceOver said. They were exploration runs that only logged, so they show green whatever was spoken. Run 38946115454 confirmed the finding on a minimal page outside Haystack. The accessible description computation takes the text of the target whatever its role, so this looks like a VoiceOver or WebKit bug, and it is to be reported to Apple through Feedback Assistant. The alert role stays for screen readers that announce an alert present on load.
- VoiceOver announces a page title only after a navigation the user started or when the user re-enters the web content, not after a script loads the page (#57, VoiceOver on macOS 26 in Playwright's WebKit). After pressing Save on the form it says "Check the form - Haystack web content", and re-entering the invalid-link page says "In This link can't be saved - Haystack web content". The error text is in the page when it loads, so VoiceOver does not announce it: the user reaches it by moving past the heading ("Enter a title of up to 200 characters."). The invalid-link page then reads the heading, "The save link has values Haystack can't use:", "list 1 item" and the reason. The refusal page reads the heading, the reason ("This link contains an access token, key, or password, ...") and the notice, and never the link.
- It runs `detectSensitiveUrl` on the submitted URL, strips it, and inserts with `ON CONFLICT DO NOTHING RETURNING` on the `(user_id, normalized_url)` index. When nothing is returned, a concurrent submission inserted first, and the page shows the existing bookmark as "already saved". No error is raised.
- The result is a page (no redirect), so reloading it shows "already saved".

On submission, the edited values are stored as the bookmark's `title` and `description`, and the raw captured values are stored alongside them as evidence for enrichment. The recent saves list and the search result cards show the confirmed `title` and `description`. There is no editing after saving.

## Sensitive URLs

Some URLs are secrets in themselves: pre-signed download links, links carrying access tokens, password reset and sign-in links, invitations, and "anyone with the link" shares. Haystack must never store them. Beyond being stored, a saved URL is sent to third parties during enrichment (the LLM provider, TypeSafe, and GitHub for repositories), so a secret URL would leave Haystack entirely.

Detection can only be partial. Many capability URLs look like ordinary URLs, so the protection has two parts.

**Telling users.** The save form shows a short notice next to the URL, stating that links containing access tokens, private shares, or sign-in and reset links must not be saved, and why. The same notice appears once on the recent saves page (and later the search page) as part of the page content, not as a dismissible banner. Keep the wording short and concrete; it is part of the interface, not a legal notice.

**Refusing recognizable patterns.** A pure function, `detectSensitiveUrl(url)`, lives in `packages/schemas` next to the normalization function. It checks an explicit, narrow list of high-confidence signals and returns the matched reason, or nothing. The initial list covers:

- query parameters used by pre-signed storage URLs, such as `X-Amz-Signature`, `X-Amz-Credential`, `X-Goog-Signature`, and the `sig` plus `se` pair used by Azure shared access signatures
- query parameters or fragments carrying credentials, such as `access_token`, `id_token`, `refresh_token`, `api_key`, `apikey`, `password`, and `client_secret`
- credentials embedded in the URL itself (`https://user:password@host`)

The function is `detectSensitiveUrl` (#20). A parameter counts only when it has a non-empty value, so a documentation anchor such as `#access_token` is accepted. Parameter names match case-insensitively. Storage signatures count in the query string only. Credential parameters also count in the fragment, including a hash route's query (`#/callback?access_token=…`). The function checks the URL as submitted, not the normalized one, which has no fragment or credentials left. A token nested inside another parameter's encoded value (for example an encoded `redirect=` URL) is not detected. The Milestone 2 check covers what this list cannot.

The list is deliberately narrow, because a match is a hard refusal with no override. Broad signals such as a parameter named `token` or `code` appear in too many legitimate URLs (documentation sites, OAuth guides) to refuse outright. Additions to the list are made in code, each with a test case, including a test proving that a similar legitimate URL is still accepted.

The check runs in three places:

1. **In the extension, before `/save` is opened.** A flagged URL never leaves the browser. The popup shows the reason and does not open the save form.
2. **On `GET /save`, and on `POST /save/address`.** For URLs that arrive by other routes (the address form, a hand-built link, later a bookmarklet or share target), the page shows the refusal's reason in the address form instead of the confirmation form (#97). The address form's POST gives the same page before it fetches anything, so a flagged address is never requested (#105). A signed-out `GET` or `HEAD` request gets the same refusal before it is sent to sign-in (see "Where the signed-out check runs" below).
3. **On `POST /save`.** The server check is the authoritative one, since the other two can be bypassed.

The refusal message states the reason in plain language (for example, "This link contains a signed access key, so it could let anyone who has it download the file") and does not echo the full URL back into the page, or into the address form's field.

**Which URLs are screened (#75).** Two URLs travel in a save: the page's own address (`url`) and the canonical URL the page declares for itself (`canonical_url`). Both are screened with `detectSensitiveUrl`, in all three places above, but a match does different things:

- **A flagged page address is refused.** Nothing is saved, and the user sees the reason. The address is what the user chose to save, so there is nothing left to save without it.
- **A flagged canonical URL is dropped, and the bookmark is saved without it.** The page is not refused. Its own address has already passed the check, and it is what the user chose to save. The canonical URL is chosen by the page, not by the user, and it is only enrichment evidence: the user never sees it, nobody edits it, and nothing links to it. A page can declare any canonical URL, including one with a session token in it, and refusing the page for that would make the user's save depend on something they cannot see or change. Dropping it matches how the popup already treats a canonical URL that fails validation (over its cap, or not an http(s) address): the field is left out and the page is still saved.
- **The dropped URL is a hint, and from Milestone 2 the Jev check uses it (#79).** A service's short share link such as `https://docs.example/s/k9Xq2` passes `detectSensitiveUrl`, while the page behind it can declare a canonical URL with `?access_token=…`. That URL is flagged and dropped, and it is the strongest sign the deterministic check gets that the page's own address is a private share. The drop stays, because refusing the page would let any page author make a page unsaveable. Instead, from Milestone 2 the save keeps the fact that a flagged canonical URL was dropped, as a flag and never the URL, and the Jev check takes it as evidence (see "Probabilistic check with Jev"). Until then nothing keeps it, so a private share behind a clean address is saved without a warning, and bookmarks saved before Milestone 2 reach the enrichment gate without the hint.
- **The form says nothing about a dropped canonical URL itself (#79).** The user never saw that value, so a notice about it would describe something they did not know was there. What the user needs to hear is whether the address they are saving is a private share, and from Milestone 2 the Jev check's warning on the save form says that, with the dropped canonical URL as part of its evidence.
- **The rule lives in one place.** `withoutSensitiveCanonicalUrl(payload)` in `packages/schemas` returns the payload without its canonical URL when `detectSensitiveUrl` flags it. The popup applies it to the validated payload just before it builds the save URL, so a flagged canonical URL never leaves the browser. `GET /save` applies it before it renders the form, so the form carries no canonical URL, and before a signed-out redirect, so the return target carries none either. `POST /save` applies it again, because a hand-built POST can carry any value. The stored row then has no canonical URL (`canonical_url` is `NULL`).
- **Nothing else is screened.** The title, the description and the Open Graph values are free text, not addresses, and `detectSensitiveUrl` does not apply to them.

**Where the signed-out check runs (#85).** A signed-out `GET` or `HEAD` request for `/save` is screened before the redirect to sign-in. The reason is storage: sign-in keeps the return target in `auth_flows.return_to`, and a URL that carries a secret is never stored (Decision 18). Before #85 the redirect came first, so a hand-built link with `?access_token=…` was written to D1, and an abandoned sign-in kept it there until the next sign-in started. `unauthenticated` in `apps/worker/src/index.ts` decides that a request needs sign-in, and for `/save` it asks `signedOutSave` in `apps/worker/src/save.ts` whether to show a page or where to return to. `signedOutSave` runs the same screening as the signed-in form (`validateCapturePayload`, `detectSensitiveUrl` and `withoutSensitiveCanonicalUrl`), so the two cannot disagree:

- **A flagged page address gets its refusal, with no redirect.** It is the page and status (400) a signed-in user gets, which since #97 is the address form with the reason. The page states the reason and never the link, so it reveals nothing and needs no session, and no `Location` header carries the link.
- **An invalid link gets its page, with no redirect.** That is the address form for an invalid address (#97), and the validation page for a link whose other fields fail. Before #85 such a link was sent to sign-in, and the page after sign-in was this same page, because signing in cannot make a link valid. Redirecting would therefore only store the link. It could also store a secret, because `detectSensitiveUrl` runs only on a validated address: a title over its cap next to `?access_token=…` is invalid, so the token is never checked.
- **A link with no captured field is sent to sign-in, and returns to `/save` (#97).** A bare `/save`, or one whose query holds only keys the form ignores, carries no value to screen, so the return target is the bare path, and the user lands on the address form after signing in. Nothing from its query is stored. From #85 until #97, a bare `/save` showed the validation page instead, without asking the user to sign in.
- **The return target holds only validated values.** The form reads the first value of each captured key, so a hand-built link can carry more: an unknown key, or a second `url` or `canonical_url`. Those values are never screened, so storing them could store a secret, which is the problem #85 fixes. The return target is therefore built from the validated payload with `URLSearchParams`, after `withoutSensitiveCanonicalUrl`, so a flagged canonical URL is left out as the form leaves it out. Validation also trims each value and omits an empty one, so an empty `canonical_url=` is absent from the return target. The form after sign-in is the form a signed-in user sees for the link as sent.
- **A link from the extension comes back unchanged.** The extension builds its save URL the same way: with `URLSearchParams`, from the validated payload. Only a hand-built link changes on the way through sign-in. It loses the values the form ignores, its values are trimmed, and it is encoded the way `URLSearchParams` encodes (for example `%20` becomes `+`). Its form is the same either way.
- **A session cookie that is no longer valid is still cleared**, on the address form and the validation page as on the redirect.
- **`HEAD` gets the same answer as `GET`.** A page request can be either, and a redirect for `HEAD` would put the link in a `Location` header even though nothing is stored.
- **`/auth/sign-in` screens a save link too (#86).** A hand-built `/auth/sign-in?return_to=/save?url=…` never passes through `/save`, so the check above would not see it. `signIn` in `apps/worker/src/index.ts` therefore runs `signedOutSave` on a return target whose path is `/save` before it stores it, and stores the rebuilt return target. A link that would get the address form's error or the validation page falls back to `/`, as a target off the origin does, and a link with no captured field is stored as `/save` (see "Return targets"). Haystack's own redirect already carries a rebuilt return target, and rebuilding it again gives the same string, so a link that enters through `/save` is stored as before (`save-url-budget.test.ts` checks this at the budget). A hand-built sign-in link is rewritten the way a hand-built `/save` link is: a clean one in another key order, or with `%20` for a space, is stored in the form `URLSearchParams` writes.

The deterministic check is part of Milestone 1.

### Probabilistic check with Jev (Milestone 2)

The deterministic list cannot recognize capability URLs that carry no telltale parameter, such as a private document share. Jev adds a probability for those. Because the question is whether a URL is safe to send to third parties, Jev must never see the raw URL.

**Redaction (#121).** A pure function, `describeUrlForJudgment(url, title, declaresSensitiveCanonical)`, in `packages/schemas/src/describe-url-for-judgment.ts`, produces the state sent to Jev: the scheme and host, the path with each segment that is not word-like replaced by a placeholder describing its shape, and the query parameter and fragment parameter _names_ with a shape placeholder for each value. Values are never included, and neither are the user name and password. The captured page title is included, since it is useful evidence and is not a secret. It takes a parsed `URL`, as `detectSensitiveUrl` does, sends nothing anywhere, and does not change the URL. It throws a `TypeError` for any scheme other than `http:` and `https:`, as `normalizeUrl` does, because Haystack saves only web pages, and a `file:`, `blob:`, `mailto:` or `data:` URL has no web host. For example, a Google Docs share gives:

```json
{
  "scheme": "https",
  "host": "docs.google.com",
  "path": "/document/d/<random:44>/edit",
  "query": [{ "name": "usp", "value": "<word:7>" }],
  "title": "Q3 planning (draft) - Google Docs"
}
```

The output's keys:

- **`scheme`** is the scheme without its colon, such as `https`.
- **`host`** is the parser's host, kept as it is. An internationalized host is therefore in punycode (`xn--bcher-kva.example`), and a port that is not the default one is included (`example.com:8443`). The host is kept on purpose, even though a host can itself be the capability: a tunnel such as `*.trycloudflare.com` or `*.ngrok-free.app` gives each tunnel a random name, and anyone with that name reaches the service behind it. Masking hosts would hide the most useful evidence Jev has, which is the service a link belongs to, and the host of a saved page is already sent to the enrichment providers.
- **`path`** is the path with every segment that is not word-like masked. Empty segments are kept, so `/docs/` and `/docs` stay different. A kept segment is shown percent-decoded, so `Quarterly%20Report.pdf` reads as `Quarterly Report.pdf`.
- **`query`** is a list of `{ "name", "value" }` pairs, in the URL's order, with repeated names kept. A list is used rather than an object, so repeated names survive and a name such as `__proto__` is only data. A name is kept, decoded, when it is word-like, and is a placeholder otherwise, because a long random key can be a secret too. A value is always a placeholder, even a word-like one, and a pair without `=` has the value `<empty>`.
- **`fragment`** describes the fragment. The part before the fragment's first `?` is a `route` when it starts with `/` (or `!/`, the older hashbang form), and it is described like the path. It is `parameters` when it contains `=` or `&`, as in `#access_token=…&state=…`. Otherwise it is an `anchor`, such as a heading's id: a word-like anchor such as `#probabilistic-check-with-jev` is kept, because it is useful evidence, and any other is masked. The part after the first `?` is always `parameters`, so a hash route's query (`#/callback?code=…`) is read the way `detectSensitiveUrl` reads it.
- **`title`** is the captured title, checked in one of two ways, depending on whether it holds the address:
  - **A title that holds the address is left out.** A title can be the address itself: the save form falls back to the full address when a page has no title, and a browser can show an untitled page's address as its tab title. Such a title may be cut to its cap partway through a value, and it can hold values too short to search for, such as `?pin=123`. Masking it piece by piece would mean reading it as a URL a second time, and it would still tell Jev nothing the description does not, so it is dropped. A title holds the address in either of two cases:
    - **It holds the URL's host followed by a path, query or fragment,** anywhere in it, so an address glued to other text (`url=https://…`, `Link:https://…`, `[doc](https://…)`) counts too. Every run of host characters (letters, combining marks such as the Devanagari virama or a Thai vowel mark, digits, `.`, `-`, `_`, `%`, and the zero-width non-joiner and joiner that IDNA allows in some scripts), or bracketed IPv6 address, right before a `/`, `?`, `#` or `\` (which the parser reads as `/`) is read as a host by the URL parser, so a host in capitals, in Unicode or percent-encoded compares equal, and a port is ignored. The title is read with a loop that looks at each character a fixed number of times, not with a regular expression, because the function is exported and a caller's title can be any length. Hosts are compared without a trailing dot and without a leading `www.` or `m.`, and a subdomain or parent of the URL's host counts too (`us02web.zoom.us` for `zoom.us`), as long as the parent has a dot. So `example.com/x?…` for `www.example.com`, or `[2001:db8::1]:8080/x?…` for that IPv6 host, holds the address. A host on its own, as in "example.com" or "Welcome to example.com", only names the site, so such a title is still a title.
    - **It is the address cut before the end of its host,** where the first case can't see it. That is a word from the scheme on that is the start of the address and goes past `https://`. Without the scheme, the start of the address is the credentials, when the URL has them, so a word that starts them and goes past the user name counts (`alice:hunter2-Sec`), and so does a whole title of four or more characters that starts them.
  - **Any other title is kept, with each whole masked part of the URL in it replaced by that part's placeholder.** Every form of a part is searched for: as written, decoded as a server reads it, and decoded with `+` kept. Parts shorter than four characters are not searched for, because they would match ordinary words (`?page=2` in "Page 2 of 10"). The start of a part is not searched for either, because it would match a word that only begins the same way (`?q=how+to+cook` in "Results for how to"). The exception is a title at its cap (`CAPTURE_CAPS.title`, or one code unit shorter, where `truncate` stops rather than split a surrogate pair). The extension, the address form's lookup and the save form's field all cut a title there, so its end may fall inside a token, and an ending of four or more characters that is the start of a masked part is replaced too. The title is read once from the start, taking the longest match at each position.
  - **A known gap (#136):** a secret that appears in the title but not, whole, in the URL passes through. One example is a token inside an encoded redirect value, which is masked in the description only because the whole value is.
- **`declares_sensitive_canonical`** is `true` when the page declared a canonical URL that `detectSensitiveUrl` flagged (see below), and is absent otherwise.

A key is absent when the URL has no such part: no `query` for a URL without parameters, no `fragment` for a URL without a fragment (or with only `#` or `#?`), and no `title` when the title is absent or empty.

**The placeholder grammar.** A placeholder is `<empty>` for an empty value, or `<class:length>`. The length counts the decoded text's characters (Unicode code points). The class is the first of these that fits:

- `digits`: only the digits 0 to 9, such as an id or a timestamp.
- `word`: word-like, by the rule below. Only a value can get this class, because a word-like segment, name or anchor is kept as it is.
- `hex`: only hexadecimal digits, all in one case, such as a hash or a signature.
- `random`: anything else, from a token to a word with a non-ASCII letter.

So a placeholder tells Jev how long a part is and which characters it uses, and nothing else. A kept part has only ASCII letters, digits, `-`, `_`, `.` and spaces, so it cannot be mistaken for a placeholder.

**The word-like rule.** A part is word-like when, after percent-decoding, it reads as words a person chose, such as `document`, `edit`, `usp`, `X-Amz-Signature`, `index.html` or `how-to-use-css-grid-in-2026`. Each limit is there because random strings break it:

- Only ASCII letters, digits, `-`, `_`, `.` and the space are allowed. Anything with `%`, `+`, `/`, `=`, `~` or a non-ASCII letter is masked, and base64 tokens usually have `+`, `/` or `=`.
- The separators (`-`, `_`, `.` and the space) split the part into pieces. Each piece is letters, a number of up to four digits, or letters and such a number joined (`v2`, `es2023`, `4k`). Letters are lowercase (`grid`), capitalized (`Roadmap`), an acronym of up to four capitals (`API`), or one of these followed by capitalized words of at least three letters (`iPhone`, `SignedHeaders`, `McDonald`). A random mix of cases, or of letters and digits, fails this, so a Google Docs id, a Dropbox id, a UUID and a Notion page's slug with its id are masked. The three letters are what mask alternating case such as `AbCdEf`: with two, about 11 in 100 random 8-letter mixed-case strings passed, and with three, about 5 in 100 do. The rule masks `LinkedIn` and `OpenAI`, and the piece rule masks `Q3Report`, on purpose: loosening it to keep such names would keep random tokens too.
- A piece has at most 20 characters, the whole part at most 80, and the whole part at most 8 digits. So a long token, a number of five or more digits, and a long number split by separators are masked.
- No piece has more than four consonants in a row, counting `y` as a vowel. This catches many random lowercase strings, such as `xkqrzpmt`. A few real words fail it, such as `strengths` and `https`, and they are masked, which is the safe direction.

The redaction errs toward masking: a borderline part is masked, because a lost word costs Jev a little evidence, while a secret that was sent cannot be taken back. Two limits remain:

- **Random lowercase letters often pass,** because telling them from words would need a dictionary. Measured with random strings, about 61 in 100 of 7 letters pass, 55 in 100 of 8 letters, and 42 in 100 of 10 letters. Formats that pass include Google Meet codes (`abc-defg-hij`, every one), Discord invites (`discord.gg/batomek`), invite codes and room names made from a word list (`/invite/apple-river-stone-cloud`, `whereby.com/cosy-room-name`, `meet.jit.si/WiseKittensTalk`), an anchor such as `#kamolerat`, and short numeric room codes (`/room/1234-5678`, `/join/1234`). Jev also sees the host, which names the service, so a Meet or Discord link still reads as one. The rule is kept as it is, because a check strong enough to mask these would also mask ordinary slugs such as `how-to-use-css`. A follow-up issue (#135) tracks it.
- **A secret that is itself word-like,** such as a parameter name used as a token, is kept like any other word.

The tests (`packages/schemas/test/describe-url-for-judgment.test.ts`) describe a set of fixture URLs: a Google Docs share, a Dropbox link, a pre-signed S3 URL, a Notion share, a magic sign-in link, an invitation link, a password reset link, a hash route carrying a token, a fragment of OAuth parameters, percent-encoded values, an internationalized host, and credentials in the URL. For each, the test reads the URL's query values, fragment values and credentials with a parser of its own, adds the path segments that must be masked, and searches the serialized output for each of them, as written and percent-decoded. It checks that a title that is the address is left out: as written, percent-decoded, either of those without its scheme, inside other words, and cut at every length past the host, with and without its scheme. Tables cover the other forms of the address above, and a title at its cap cut inside a token. It checks that a title of ordinary text made of the URL's secrets, in every form, has each of them masked. It also checks that every value is a placeholder, and that everything else is kept word-like text or a placeholder. Tables cover the word-like rule and the placeholder grammar.

**The dropped canonical URL is evidence (#79).** When the page declared a canonical URL that `detectSensitiveUrl` flags, the state also says so, as `"declares_sensitive_canonical": true`, and the criteria describe it as a strong sign that the address works as a key. The canonical URL itself is never sent, in raw or redacted form. So `describeUrlForJudgment` takes the flag as well as the URL and the title, and adds `"declares_sensitive_canonical": true` only when the flag is set.

How the fact reaches the check: `withoutSensitiveCanonicalUrl` will also report whether it dropped a flagged URL, so each place that drops one (the popup, `GET /save` and `POST /save`) can record it. The popup passes the flag in the save URL. `GET /save` carries it forward as a hidden input, or sets it when it drops the URL itself, and `POST /save` stores it in `sensitive_canonical_dropped`, so the enrichment gate has it for a bookmark checked later. The flag is a few characters, so the popup never drops it to make the save URL fit. The Milestone 2 work decides the query key.

What the flag is worth: like every other captured value, it comes from the client, so it is evidence and not proof. It is also chosen by the page, so a page author can declare a canonical URL with a token in it and make a public page warn, and, until the user releases it, be Held. That costs the user a click, not the save, which is why a high noul is a warning and never a refusal. A hand-built request that leaves the flag out only loses the hint for that save.

**The question.** One Noul: "Would this link grant access to something private, such as a document, file, account, or invitation, to anyone who has it?" The criteria describe a true answer as a link that works as a key (shares, signed links, invitations, sign-in and reset links, tokenized links) and a false answer as a link to a public page. Write the final wording after reading the Noul page in the live documentation.

_Worded 2026-10-22 (#122), after reading the [Noul page](https://docs.typesafe.ai/primitives/noul.md) and [Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md)._ The question is `SENSITIVITY_QUESTION` in `apps/worker/src/enrichment/jev-questions.ts`. The state is `{ "link": <describeUrlForJudgment's output> }`, because the [State page](https://docs.typesafe.ai/concepts/state.md) recommends named fields, and the question can then point at `link` by path. Jev reads a question literally and has no other way to know what a placeholder means, so the instructions say it:

- **`question`:** "Would the web address that `link` describes give anyone who has it access to something private, such as a document, a file, an account or an invitation?" A high value means yes, as the Noul page asks.
- **`about_link`:** "`link` describes the address without its values. Each query value, each fragment value and each part of the address that does not read as words is replaced by a placeholder: `<empty>`, or `<class:length>`, where the class is digits, word, hex or random, and the length counts its characters. `link.title`, when present, is the page's title. `link.declares_sensitive_canonical` is present, and true, when the page named a canonical address that Haystack recognized as carrying a secret."
- **`criteria.true`:** "The address works as a key: whoever has it gets in without signing in, as with a shared document or file, a signed download link, an invitation, a sign-in or password reset link, or an address that carries an access token. `link.declares_sensitive_canonical` is a strong sign of this."
- **`criteria.false`:** "The address leads to a public page, such as an article, documentation, a product page, a search or a repository, which anyone can open without the address being shared with them."

The instructions and the criteria say the same thing from both sides, because the jaggedness page warns that Jev does worse when they disagree. The Noul page suggests trying a question with and without criteria. That comparison needs real bookmarks and their answers, so it belongs to Phase 9's review of the first enrichments.

**Policy, in code.** The deterministic match remains a hard refusal. A noul at or above `SENSITIVE_WARN_THRESHOLD` (configuration) is a warning, not a refusal, because a probability will produce false positives. If Jev is unavailable, saving proceeds on the deterministic check alone, with `sensitivity_noul` left empty, and the enrichment gate checks the bookmark later. A TypeSafe outage must never block saving.

**On the save form.** `GET /save` runs the check before rendering. Above the threshold, the form shows a warning explaining why the link looks private and adds a required checkbox: "This link does not give access to anything private." `POST /save` runs the check again rather than trusting anything from the form, and rejects the submission if the result is above the threshold and the checkbox is not ticked. The stored bookmark records the noul, when it was checked, and the acknowledgment.

**As an enrichment gate.** The enrichment module runs the check as its first step for any bookmark whose `sensitivity_noul` is empty, which covers everything saved in Milestone 1 and anything saved during a Jev outage. A bookmark at or above the threshold without an acknowledgment becomes Held: it is not sent to GitHub, to the `kind` question, or to the LLM provider. A Held bookmark does not count as a failed attempt.

**Reviewing Held bookmarks.** A page at `/held` lists them with their titles and hosts. The same page also lists Failed bookmarks with a retry action (see "Enrichment sweep"). Each Held bookmark has two actions: release (the user confirms the link is not private, which sets the acknowledgment and lets the sweep enrich it) or delete (which removes the bookmark and everything attached to it). Both are POST actions with the usual session and `Origin` checks. Deletion here uses the same endpoint as everywhere else (see "Deleting bookmarks").

**Calibration.** Stored bookmarks keep their noul and acknowledgment, which shows how often the warning fired on links the user considered fine. When a warning is shown but the bookmark is never saved, log only the noul and the fact that a warning was shown, never the URL.

## Deleting bookmarks

A bookmark can be deleted by its owner from the recent saves list (Milestone 1), the search results (Milestone 3), and the review page at `/held` (Milestone 2). All three use one endpoint, `POST /bookmarks/:id/delete`, with the usual session and `Origin` checks.

The server looks the bookmark up by ID _and_ the session's user ID in the same query. If there is no match, it returns 404, whether the bookmark does not exist or belongs to someone else, so the response never reveals that another user's bookmark exists. The delete button is only rendered for bookmarks the current user owns; in v1 every bookmark a user can see is their own, but the server check is what enforces it.

Deletion is permanent and removes the bookmark with its enrichments, failure records, and search answers. The URL can be saved again afterward. Search runs themselves are kept, so the evaluation harness must tolerate labeled bookmark IDs that no longer exist.

**Interaction.** Each result card and list item has a real `<button>` inside a small `<form method="post">`, with an accessible name that includes the title (for example, "Delete Vitest browser mode guide"), so a screen reader user hearing a list of delete buttons knows which is which. Without JavaScript, the button leads to a confirmation page with a single confirm button. With JavaScript, confirmation happens in a native `<dialog>` opened with `showModal()`, which makes the rest of the page inert and handles Escape. It does not trap Tab: from the first or last control, Tab and Shift+Tab can move to the browser's own toolbar, and the next Tab returns to the dialog. After deletion, the item is removed, focus moves to the next item (the previous one when the bottom item was deleted, or the list heading when the list is empty), and the live region announces the deletion.

Deleting without JavaScript was implemented in #42:

- Each list item's form posts to `POST /bookmarks/:id/delete`. Without `confirm=yes` in the body, the endpoint only shows the confirmation page, which posts again with it. A body that is not a form is treated as unconfirmed. The JavaScript dialog (#43) will post `confirm=yes` directly.
- The button is `aria-labelledby` itself and the item's `<h2>`, so its name is "Delete" followed by the title, and the visible text stays "Delete".

## Agent access (Milestone 4)

Both agent surfaces call the same `searchBookmarks(userId, query, { channel, inputMode })` service as the web page, so ranking, thresholds, logging, and the exclusion of Held bookmarks behave identically. `channel` is recorded on each search run, so agent searches can be analyzed separately from human searches.

**Tool design.** One tool, `search_bookmarks`, takes a natural-language `query` string and returns the ranked results: title, description, URL, and kind. It does not return enrichment internals, probabilities, or anything else from the database. The tool description tells the agent what Haystack contains and that results are the signed-in user's own saved resources. The result shape is defined once, as a Valibot schema in `packages/schemas`, and shared by both surfaces.

**WebMCP.** The search page registers the tool with the browser's WebMCP API when it is available (feature-detected, see Q9). The tool calls the existing `/api/search` endpoint with the page's session, so it needs no new authentication and only works while the user is signed in with the page open. Because WebMCP is in-browser and human-present, it is the lower-risk surface and is built first.

**Remote MCP server.** A `/mcp` endpoint on the same Worker implements the 2026-07-28 specification with its stateless core: there is no initialization handshake and no session, so every request is self-contained and handled like any other Worker request. It exposes only the search tool. Authorization follows the MCP specification (see Q8). Each MCP request resolves to a Haystack user, is checked against `ALLOWED_EMAILS` like a session, and is subject to a per-user rate limit, because agents can issue searches far faster than a person.

Write tools (saving and deleting through agents) are out of scope for Milestone 4 and listed in the backlog.

**Untrusted text in tool results.** Search-only does not mean the risk is small for the user. Titles and descriptions in tool results come from web pages, and the agent that reads them may have other tools, such as email, file access, or a shell. A bookmarked page with an injected instruction in its description then reaches that agent. Haystack cannot control the agent. It can return results as structured data (fields, not prose), keep descriptions length-capped, and state in the tool description that the result fields are third-party page text and are not instructions. Record this risk in the documentation for connecting an MCP client.

## Authentication

### Site sign-in

The site uses the Google OpenID Connect authorization code flow with PKCE and a `state` parameter. The callback exchanges the code, verifies the ID token (issuer, audience, expiry, signature against Google's published keys, and `email_verified`), then checks the email against the `ALLOWED_EMAILS` allowlist. Users are keyed on the `sub` claim, not the email address, because the email address can change.

On success, the server creates a session with a random ID, stores only its SHA-256 hash in `sessions`, and sets the raw ID in a cookie with the `__Host-` prefix and the `HttpOnly`, `Secure`, `SameSite=Lax`, and `Path=/` attributes. Every state-changing request also checks the `Origin` header as CSRF protection alongside `SameSite`. Sign-out deletes the session row and clears the cookie.

Sessions last 30 days and slide: a request in the second half of a session's life extends its expiry, so the database is not written on every request. Every request also checks the session user's email against `ALLOWED_EMAILS`, so removing an address takes effect immediately rather than when the session expires. The allowlist check needs the email stored on the user row, which is refreshed at each sign-in. The session lookup deletes an expired row it finds, and the scheduled handler deletes the rest from Milestone 2.

Every page and API route except `/auth/*` requires a session. Unauthenticated page requests redirect to sign-in, and unauthenticated API requests return 401. A page request is a GET or HEAD whose `Accept` header includes `text/html`; every other request counts as an API request. Static assets (CSS, JavaScript, fonts, images) are public, and must never contain user data. Implemented in #25:

- The cookie is `__Host-session`. The session ID is 32 random bytes, base64url-encoded, and the stored hash is its hex SHA-256.
- `ALLOWED_EMAILS` is a comma-separated `vars` entry, matched without regard to ASCII case. Only A to Z are folded, so a non-ASCII lookalike does not match.
- The `Origin` check applies to every method other than GET, HEAD, and OPTIONS, including `/auth/*`.
- Sign-out is `POST /auth/sign-out`, which redirects to `/auth/signed-out`.

By default, Workers serves a matching static asset without running the Worker. Keep all HTML out of the assets directory so that every page goes through the Worker. If an HTML route must ever live in the assets directory, configure Wrangler to run the Worker first for that path (verify the current `run_worker_first` configuration) and add a test proving it redirects without a session.

Implemented in #26:

- **Redirect URI:** `<origin>/auth/callback`, from the request's own origin, in both the authorization and the token request.
- **Scope:** `openid email`.
- **No nonce:** OIDC Core makes it optional for the code flow, and `oauth4webapi` then rejects a token that carries one.
- **Login CSRF protection** (RFC 9700, section 4.7.1): sign-in sets `__Host-auth_flow` to the `state` (10 minutes, `SameSite=Lax`, so it survives Google's redirect back). The callback rejects a `state` that doesn't match the cookie before it uses up the flow, and clears the cookie on every outcome. Starting sign-in in a second tab replaces the cookie, so finishing the first tab fails, and the user signs in again.
- **A successful sign-in deletes the browser's previous session**, if it had one.
- **Expired `auth_flows` rows** are deleted whenever a new flow is created.

### Return targets

When an unauthenticated request needs sign-in, the path and query to return to are stored server-side with the OAuth `state`, not passed through as a free-form parameter. They go in the `auth_flows` table together with the PKCE verifier. A cookie is not used for this, because a `/save` return target holds the captured page data and can exceed the roughly 4 KB that browsers allow for one cookie. An `auth_flows` row is used once, deleted in the callback, and rejected after it expires. The session lookup deletes expired rows it finds, and the scheduled handler cleans up the remaining ones from Milestone 2. Before redirecting after sign-in, the server confirms that the target is a relative path on the Haystack origin. Anything else falls back to `/`. The check resolves the target against a placeholder origin. It then also rejects a resolved path that starts with `//`, because dot segments collapse during parsing (`/.//host` becomes `//host`). This prevents the sign-in flow from becoming an open redirect.

`/auth/sign-in` also screens a return target whose path is `/save` before it stores it, the way a signed-out `/save` is screened. A save link the form would read therefore has no flagged secret written to `auth_flows`, whichever way the user arrives: through `/save`, or through a hand-built sign-in link. The path is compared after `safeReturnTarget` has resolved dot segments and removed tabs, so it is the path the router compares. The stored target is rebuilt from the validated fields the form reads. A save link that the form would refuse or reject falls back to `/`, like a target off the origin, rather than ending the sign-in, because the request is still a request to sign in. The person then lands on the recent saves, which have the address form, without the page that would have said what was wrong with the link. But only a hand-built link reaches this, because Haystack's own redirect is screened first (see "Where the signed-out check runs" under "Sensitive URLs").

A save link with no captured field, such as a bare `/save`, is stored as `/save` (#97). It holds no value, so nothing that could be a secret is written, and after sign-in it shows the address form. Any query or fragment it had is dropped, because none of it is a field the form reads. Before #97 it fell back to `/`, because a bare `/save` got the validation page. Other targets are stored as given, because only the save form reads an address from its query. That includes a path the router does not treat as the form, such as `/save/` or `/Save`, which answers 404 after sign-in: a secret in its query is stored, but nothing reads it, and only the person who built the link could have put it there.

### Rules that hold everywhere

No endpoint accepts a `user_id` from the client. Pages never send `Referrer-Policy: no-referrer`: with it, browsers send `Origin: null` on same-origin form posts, and the `Origin` check would reject every one. Use `strict-origin-when-cross-origin` or `same-origin`. Session IDs are compared by hash lookup, not string equality on raw values. Every query that reads or writes user data filters by the authenticated `user_id`, and a test for each endpoint proves that one user cannot read another user's bookmarks or search logs.

## Secrets and configuration

`.env.schema` declares every variable for varlock, with sensitive values resolved from 1Password. varlock resolves a schema from the directory where it runs. The root `.env.schema` holds shared items (`APP_ENV`), and `apps/worker/.env.schema` imports it with `@import(../../)` and declares the Worker's own variables and the 1Password plugin. The root `varlock load` in `quality` therefore needs no 1Password access, and CI needs no secrets. varlock and 1Password are used for local development only, and the 1Password desktop app authenticates (`allowAppAuth=true`, account `my.1password.com`). Deployed Workers read secrets set in Cloudflare, and CI needs no secrets. "Deploys" below describes the deploy procedure.

Local development goes through `varlock-wrangler`: `vp run dev` in `apps/worker` runs `varlock-wrangler dev`. varlock passes the resolved values to Wrangler through a named pipe (`--env-file` pointing at a FIFO), so secret values appear neither on disk nor in process arguments. This was verified in #8. Every item in `apps/worker/.env.schema` is sensitive unless it is marked `@public`, so varlock masks it in its output. Wrangler then loads them into its own `process.env`, so the local `workerd` processes inherit the secret in their environment, which only the same user can read. Removing that copy is suggested upstream in cloudflare/workers-sdk discussion #16197. `apps/worker/vite.config.ts` keeps the plain `cloudflare()` plugin and not varlock's Vite wrapper. The wrapper resolves every variable when the Vite configuration loads, so every build, including the build test in CI, would need 1Password. _Decided 2026-10-13 (#43, resolving #15): local development stays on `varlock-wrangler dev`. Static assets are plain, unbundled files in `apps/web/public`, with no build step. `apps/worker/wrangler.jsonc` sets `assets.directory` to that folder, which `wrangler dev` and the test harness (and so the Playwright fixtures) read. `vp build` ignores that field and copies Vite's `publicDir` instead, so `apps/worker/vite.config.ts` names the same folder, and the build test checks that the dialog script is in the output. A request for an existing file is served without running the Worker, so the Worker's headers do not apply: `apps/web/public/_headers` adds `nosniff` (the CSP stays on the HTML, where it has effect). The asset server sends `Cache-Control: public, max-age=0, must-revalidate` with an ETag, which is right for unhashed file names. `vp check` type-checks the scripts through `apps/web/tsconfig.json` (`checkJs`). A `vp dev` move would need the Vite plugin's experimental `_headers` support, so it is not planned._

`apps/worker/wrangler.jsonc` declares the secret names in `secrets.required`. Deploy fails if a required secret is missing, so the list grows with each milestone instead of listing everything up front. A secret is added to the list in the same change as the first code that reads it, even when nothing in production calls that code yet, as with `TYPESAFE_API_KEY` (#122), so the deploy fails before a caller ships rather than after. The one exception is `GOOGLE_CLIENT_SECRET`, which #8 added before Phase 2 uses it, to prove the secrets pipeline. `secrets` and `flagship` are not inherited by Wrangler `env.*` blocks, so if staging or production become named environments, each block repeats both.

Because `secrets` is declared, Wrangler also reads secrets from `process.env` in local dev and in the test harness. A test that needs a secret sets it through the harness's `secrets` option. Run `vp test` without varlock, so the real values never reach the tests. The harness does not bind a required secret that it cannot find, so the value is `undefined` even though the generated `Env` type says `string`.

```jsonc
{
  // Milestone 1: Capture
  "secrets": {
    "required": ["GOOGLE_CLIENT_SECRET"],
  },
  // Milestone 2: Enrichment adds (the TypeSafe key also powers the sensitivity check)
  //   "TYPESAFE_API_KEY" (added in #122), "ANTHROPIC_API_KEY", "GITHUB_TOKEN" (added in #123)
  //   (plus the AI Gateway token, if the gateway is configured to require one)
  //
  // Post-v1, with the OpenAI and OpenRouter adapters:
  //   "OPENAI_API_KEY", "OPENROUTER_API_KEY"
}
```

`TYPESAFE_API_KEY` is in `apps/worker/.env.schema` as an optional item with no value (#122), because the key had no 1Password item when it was added. Local development therefore runs without it, which is fine while nothing calls Jev. When the key is stored in 1Password, the item gets its `op(...)` reference and loses `@optional`, as `GOOGLE_CLIENT_SECRET` has. `GITHUB_TOKEN` is there the same way, for the same reason (#123), and joined `secrets.required` in the same change, so it must be set in Cloudflare before the next deploy. "GitHub enrichment" records the settings the token is created with.

Non-secret static configuration, such as the base URLs for Jev, the LLM providers, GitHub, and Google (so integration tests can point them at fixtures), the AI Gateway account and gateway IDs, the model chosen for each provider, the sweep frequency and attempt limit, `SENSITIVE_WARN_THRESHOLD`, `GOOGLE_CLIENT_ID`, and `ALLOWED_EMAILS`, goes in `vars`. Never run `wrangler secret put` with a value in the command line.

**Runtime switches** are Flagship flags (decision 20): the search questions (`both`, `noul`, or `score`), the display signal, the Noul and Score thresholds, the request mode, whether the sweep is enabled, and the sweep batch size. These are the settings that change during evaluation and operation. `SENSITIVE_WARN_THRESHOLD` and `ALLOWED_EMAILS` stay in `vars` on purpose. Changing the sensitivity threshold changes which bookmarks are Held, and changing the allowlist changes who can sign in, so both should be reviewed changes that go through a deploy.

The Worker reads flags through a binding, declared as follows (field names checked against the Wrangler 4.147.0 configuration schema):

```jsonc
{
  "flagship": [{ "binding": "FLAGS", "app_id": "<APP_ID>" }],
}
```

One configuration module reads every flag once per request, or once per sweep run, and passes the values on. No other code calls the binding. Each flag's default value is a constant in that module, so the defaults are reviewed in code. The typed getters return the default for a missing flag, a flag that cannot be evaluated, or a type mismatch, and they throw for an empty or non-string key and for any other error (see Q13). The module therefore uses constant, non-empty keys, and it catches any error from the binding and uses the defaults, so a Flagship outage means the Worker runs with those defaults. The defaults are the safe values: both questions, the Score signal, batched mode, and the sweep enabled with a batch size of 3. Q3 sets a ceiling of 3 on the batch size, because a fourth bookmark could take a run over the subrequest limit. The default must never be above it, because the defaults are what a Flagship outage runs with. The module also checks the live flag: a value that isn't a whole number from 1 to the ceiling is replaced by the default, so a mistyped flag can't take a run over the limit either (#128).

### Deploys

**The deploy command is `vp -C apps/worker run deploy`, which runs `vp build && wrangler deploy` in `apps/worker` (#16).** Every command in this section runs from the repository root, as in "Backups and restore" under "Data model". The Cloudflare Vite plugin writes the built Worker and its Wrangler configuration to `dist/haystack/`, and writes `.wrangler/deploy/config.json`, which points at that configuration. Plain `wrangler deploy` follows the pointer and reports "Using redirected Wrangler configuration". Building in the same command means a deploy never uploads an old build. Git ignores both folders. `vp -C apps/worker run deploy --dry-run` builds and bundles the Worker and prints its bindings without contacting Cloudflare, because the script passes the flag on to Wrangler. It does not check that the secret is set in Cloudflare, so it cannot stand in for the first-deploy check below.

**Never run `varlock-wrangler deploy`.** varlock's Wrangler wrapper resolves `apps/worker/.env.schema` and hands every sensitive value to Wrangler through `--secrets-file`, so it would upload the local development secrets to the deployed Worker (`handleDeploy` in `@varlock/cloudflare-integration` 1.6.1). Plain `wrangler deploy` uploads a secret only when it is given `--secrets-file`. It turns `.env`, `.dev.vars` and `process.env` into Worker bindings only for local development (`getVarsForDev` in Wrangler 4.149.0). On a deploy it reads `.env` only for its own settings, such as an API token. varlock is for local development (`vp run dev` in `apps/worker`) only.

**Run the deploy from a shell that does not have a secret in its environment, and keep `apps/worker` free of `.env` and `.dev.vars` files.** `vp build` copies any `GOOGLE_CLIENT_SECRET` it finds in either place into `dist/haystack/.dev.vars`, for `vite preview`, and the file stays there in plain text until the next build. Plain `wrangler deploy` does not upload it, but it is the secret on disk. The build's warning about the missing secret suggests adding it to `.dev.vars` or `.env`, so ignore that warning: the secret belongs in Cloudflare, not the build.

**Secrets are set in Cloudflare with `wrangler secret put <NAME>`, one at a time, or in the Cloudflare dashboard.** The command has no option for the value. In a terminal it asks with a masked prompt, and otherwise it reads the value from standard input. Never put a value on the command line, where shell history and the process list keep it. Piping it from 1Password means it is never typed, copied to the clipboard or written to disk. Wrangler trims the trailing newline that `op read` prints. Log in first with `vp -C apps/worker exec wrangler login`, and check with `vp -C apps/worker exec wrangler whoami`, because the piped command has no terminal, so it cannot open the browser to log in.

```sh
(
  ref=$(sed -n 's/^GOOGLE_CLIENT_SECRET=op("\(.*\)")$/\1/p' apps/worker/.env.schema) &&
    [ -n "$ref" ] &&
    secret=$(op read "$ref") &&
    [ -n "${secret//[[:space:]]/}" ] &&
    printf '%s' "$secret" | vp -C apps/worker exec wrangler secret put GOOGLE_CLIENT_SECRET
)
```

**The command reads the value once and refuses an empty one, because `wrangler secret put` stores an empty secret without complaint.** In a plain pipe, the right-hand command runs even when `op read` fails, for example because 1Password is locked or the reference does not resolve, and then Wrangler reads empty input. A 1Password field that is empty is a second case, because `op read` prints nothing and still exits successfully. In Wrangler 4.149.0 the Worker's `secret put` handler trims the input and uploads whatever is left, while the Secrets Store `secret create` handler throws "Need to pass in a value when creating a secret." for an empty value. `secrets.required` does not help, because it only checks that the secret exists. The first production deploy stored an empty `GOOGLE_CLIENT_SECRET` this way, and every sign-in failed (#98). The command stores the value in a shell variable first, and only starts Wrangler when the reference was found, `op read` succeeded, and the value has at least one character that is not whitespace. Wrangler trims the value, so one made only of whitespace would also be stored empty. Each step must succeed before the next runs, so a missing reference or a failed `op read` stores nothing. The parentheses run it all in a subshell, so `ref` and `secret` disappear when it ends, and its exit status is the status of the upload: a failure anywhere is a non-zero status, not a quiet success. It works in zsh and bash, which both support `${secret//[[:space:]]/}`. This is safe for the value because `printf` is a shell builtin, so the value never appears in the process list, and shell history records the command text, not the value. The `sed` expression takes the reference from `apps/worker/.env.schema`, which holds references and no values.

**After setting a secret, check that it works.** The Worker has no `observability` setting, so Cloudflare stores no logs, and the log line is only visible live. Start `vp -C apps/worker exec wrangler tail haystack` (or the dashboard's live log stream) before the sign-in. For `GOOGLE_CLIENT_SECRET`, start a sign-in at `/auth/sign-in`, which must reach Google's account page, and complete it there. The page that follows must not be "Sign-in failed". If it is, the log shows `Sign-in failed: GOOGLE_CLIENT_SECRET_EMPTY` for an empty secret, and any other code points at a different cause.

**The first deploy needs the secret set before the Worker exists.** Because of `secrets.required`, a deploy fails when a listed secret is not set. For a Worker that does not exist yet, Wrangler uploads the static assets and then stops with an error, before it creates the Worker. Its message suggests `wrangler deploy --secrets-file`. Don't follow that suggestion, because it means writing the secret to a file. Run `wrangler secret put` first instead. When no Worker has the configured name, it asks whether to create one. Without a terminal, as in the pipe above, it creates the Worker without asking. The Worker is a placeholder whose fetch handler returns nothing, so any request to it fails, and it holds the secret and no data. The first deploy replaces it. On the first deploy, run `vp -C apps/worker run deploy` once before setting the secret, to confirm that it fails and that no Worker named `haystack` exists afterwards (`vp -C apps/worker exec wrangler deployments list`, or the dashboard). That is the check #16 asks for.

**A secret added later** (Milestone 2 adds three) is set with `wrangler secret put` before deploying the change that adds it to `secrets.required`. `wrangler secret put` redeploys the code that is already deployed, with the new secret, which is harmless because that code does not read it yet. For a Worker that already exists, Cloudflare rejects a deploy that is missing a listed secret, and Wrangler reports the missing names.

**The order for each deploy:**

1. `main` passes `quality`.
2. Take the export with `vp -C apps/worker run db:export:remote`, then apply the migrations with `vp -C apps/worker run db:migrate:remote` (see "Backups and restore" under "Data model"). Migrations go first, because every migration stays compatible with the Worker version that is already deployed.
3. Run `vp -C apps/worker run deploy`.

**Production shares the local development Google OAuth client.** _Decided 2026-10-18 (#16)._ Haystack has one user, so one client keeps the Google setup in one place:

- The production redirect URI, `https://<worker>.<subdomain>.workers.dev/auth/callback`, is added to the client next to `http://localhost:5173/auth/callback`.
- `GOOGLE_CLIENT_ID` stays a single value in `vars`.
- Cloudflare holds the same secret as the 1Password item.

The cost is that production and local development share one secret. The development copy passes through the local Wrangler processes' environment (see above), so a leak there is a leak of the production secret too. Sharing also leaves `http://localhost:5173/auth/callback` as a valid redirect for production sign-in. That is harmless, because sign-in uses PKCE and keeps its state on the server (`auth_flows`), so an authorization code sent to a local port is useless without the verifier and the secret. If the secret leaks:

1. Rotate the secret in Google Cloud Console.
2. Update the 1Password item.
3. Set the new value with `wrangler secret put`.

A separate production client becomes worth having if anyone else runs a development copy.

## Dependency updates

Dependabot proposes npm and GitHub Actions version updates weekly, and waits 7 days after a release before proposing it (`.github/dependabot.yml`). The schedule and the wait apply to version updates only: a security update can arrive at any time. Some packages only work at matching versions, but Dependabot updates each package in its own pull request unless a group says otherwise (#60).

- **Groups.** Each group below exists twice, once for version updates and once for security updates, because a group covers only version updates unless it says otherwise.
  - `wrangler` and `@cloudflare/vite-plugin`: the plugin checks that the installed Wrangler matches the version it requires, and fails the build otherwise.
  - `varlock` and `@varlock/*`: each plugin requires the `varlock` release it shipped with, and imports its internals.
- **Calavera manages `.github/dependabot.yml`,** but cannot express groups yet (create-project-calavera#691), so the groups were added by hand with approval. Until that issue is resolved, re-add the groups after any `calavera apply` that rewrites the file.
- **A Wrangler update can also need the Worker types regenerated.** Wrangler bundles the Workers runtime (workerd), and `apps/worker/worker-configuration.d.ts` records the runtime version it was generated from. When an update moves the runtime, `types:check` fails in CI ("Types at worker-configuration.d.ts are out of date", as in #52). Run `vp -C apps/worker run types` on the pull request's branch and commit the result.
- **`vite-plus` and the `vite` alias cannot be grouped.** The workspace catalog in `pnpm-workspace.yaml` pins `vite` to `npm:@voidzero-dev/vite-plus-core@…`, the Vite build that Vite+ ships, so that the Cloudflare plugin and Vite+ use the same Vite. Each `vite-plus` release requires exactly the same `vite-plus-core` version, but Dependabot does not update the alias. In #51, its commit moved `vite-plus` to 1.1.0 and left the alias at 1.0.0, which installed two copies of Vite. (dependabot-core#15847, mainly about Bun, notes that version updates skip aliased packages in npm and pnpm projects too.) So every Dependabot pull request for `vite-plus` needs a commit that sets the alias to the same version and reinstalls. A mismatch does not always fail CI: in #51 it did only because the Cloudflare plugin's types clashed. Vite+ tracks the problem in [voidzero-dev/vite-plus#2356](https://github.com/voidzero-dev/vite-plus/issues/2356), including a proposed check that fails when the two versions differ. If the manual step becomes a burden before that ships, add a Haystack check that compares the two versions.
- **`@types/node` is on major 25 (#63).** Node 24 is the LTS line and 26 is the newest release, so 25 was accepted as safe. Dependabot skips major 26 because of a `@dependabot ignore this major version` comment on its pull request (#50). That setting is stored by Dependabot, not in the repository, so `dependabot.yml` does not show it.

## Testing strategy

**User journeys** (#115) say in plain language what a person can do with Haystack, and what happens when something goes wrong. They are Gherkin scenarios in `docs/journeys/`, one `.feature` file per area, and they quote the wording a person sees and hears from the code. They are documentation and the input for the Playwright tests, and they do not run, so there is no Cucumber and no step definitions. Each scenario is tagged with the tests that cover it (`@playwright:`, `@integration:`, `@voiceover:` or `@unit:`, followed by the test file's path), or with `@untested`, and `docs/journeys/README.md` lists the untested journeys as candidates for new tests. New behaviour gets its journey written before or with its tests, and a change to behaviour or wording changes its journeys in the same pull request.

**Unit and integration tests** run with `vp test` (Vitest 5, bundled with Vite+). See Q10 (a) for the reasons behind this approach. Pure modules have plain unit tests. Integration tests start the Worker in the local Workers runtime with Wrangler's `createTestHarness`, and use a real local D1 binding. Before running, they apply the same migration files as production with the harness's `applyD1Migrations`, so the tested schema is always the migrated schema. One test applies the migration files itself instead (`apps/worker/test/enrichment-migration.test.ts`), because it seeds Milestone 1 rows between the first migration and the enrichment migration to show that those rows survive it (#120). Jev, LLM, GitHub, and Google calls go to a small HTTP server that the test starts and that serves recorded responses. The base URLs for those services are `vars`, which the tests override. Tests cover Haystack's own behavior and decisions. They do not check that a library or tool (for example Wrangler, Vite+, Drizzle, or `oauth4webapi`) behaves as documented. A library or tool that fails or behaves unexpectedly is reported upstream, with a patch where possible, and is not worked around in silence. External services that Haystack calls at runtime (Jev, the LLM providers, GitHub, Google, and Flagship) are different: their responses are untrusted input. Haystack validates them, retries, and falls back as this plan describes, and tests cover that handling. The `evals/` contract check below compares Haystack's recorded fixtures and schemas with the live services. It is not a test of those services. No unit test calls a live paid API. Recorded fixtures can drift from the live APIs, so `evals/` also contains a small contract check. It sends one live request to each external API, validates the response with the same Valibot schemas the clients use, and runs before each milestone deploy.

**Markup validation.** The Worker renders every page (decision 1), so its pages are not `.html` files, and the `html-validate "**/*.html"` script (`lint:html`, not part of `pnpm quality`) does not see them. Integration tests render each page through the test harness and validate the result with html-validate's programmatic API and the existing `.htmlvalidate.json` configuration (issue #3). The extension's popup page, `apps/extension/index.html` (#70), is the only `.html` file, so it is the only input of `vp run lint:html`. It follows the formatter's style, a lowercase `<!doctype html>` and self-closing void elements, because `vp check --fix` rewrites it that way on every commit. `apps/extension/.htmlvalidate.json` sets `doctype-style` to `lowercase` and `void-style` to `selfclosing` for that directory only. html-validate merges it over the repository's `.htmlvalidate.json`, so the presets still apply, and the Worker's rendered pages keep the repository's style.

**End-to-end tests** use Playwright for the search page and the save form, including keyboard-only operation and an axe accessibility scan. The extension is tested in Chromium by launching a persistent context with `--load-extension`. Playwright cannot load Firefox extensions, so Firefox is covered by a documented manual check using `web-ext run`.

Set up in #11:

- The browser tests live in `apps/worker/e2e` (`*.e2e.ts`, so Vitest does not pick them up), because they test the pages the Worker renders. The extension tests (Phase 5) live with the extension.
- Each Playwright worker process starts the Worker with `createTestHarness` and applies the migrations (`e2e/fixtures.ts`), and `baseURL` is that Worker's origin. So the browser tests need no dev server and no secrets. Its `signIn` fixture (#31) seeds a signed-in user in D1, gives the browser the session, and checks that the Worker accepts it.
  - **Chromium gets a real cookie,** with the attributes the Worker sets. `addCookies` with an `http:` `url` clears `Secure`, which a `__Host-` cookie needs, so Chromium refuses it. With a `domain` and `path` instead, the cookie is accepted (#70). A header would not do for Chromium: it does not send Playwright's extra HTTP headers on the GET that follows a 303, which the address form's lookup ends with (#105).
  - **WebKit gets a `Cookie` header** that Playwright adds to every request (`setExtraHTTPHeaders`), as both browsers did before #105. WebKit keeps it on the GET after a 303. A cookie does not do for WebKit, because whether it sends a `Secure` cookie to http://127.0.0.1 depends on the macOS it runs on. On macOS 27.0.1, Playwright's WebKit build 2370 sent it, headless and headed. On the macOS 26 CI runner, the same build did not: in the trace of PR #107's VoiceOver run, `addCookies` succeeded, the first `GET /save` was answered with a redirect to sign-in, and the browser went on to Google. The VoiceOver tests on `main`, which used the header, passed on the same runner.
  - **The check** loads the signed-out page, which looks up no session, and asks for `/` with the page's own `fetch`. The Worker answers a request that is not for a page with 401 when it has no session, rather than a redirect, so a test without a session fails at once, and the browser never leaves for Google. A navigation to a signed-in page could not be stopped there, because Playwright's routes do not see the hops of a redirect. `signOut` takes the session away whichever way it was given.
  - **`e2e/session.e2e.ts`** covers the sign-in that the VoiceOver tests use: the address form's lookup and its 303, a save through the confirmation form, and the check failing for a browser with no session. It runs in Chromium with the other browser tests, and in headed WebKit as the first project of the VoiceOver configuration (`webkit-session`), which the VoiceOver tests depend on. So on the macOS runner a broken sign-in fails in seconds, without starting VoiceOver. Locally, `vp exec playwright test --config playwright.voiceover.config.ts --project webkit-session` runs it in WebKit, also without VoiceOver.
- Only Chromium is used, with one exception: `session.e2e.ts` also runs in headed WebKit, as the `webkit-session` project of the VoiceOver configuration (`playwright.voiceover.config.ts`).
- They run as part of `vp run quality` (`vp run -r test:e2e`). Before the first run, install the browser once with `vp -C apps/worker run e2e:install` (Chromium's headless shell). Do it again after a Playwright upgrade. CI installs the same browser before `quality`.
- axe runs every rule, including the best-practice rules, with no `withTags` filter. The best-practice rules (landmarks, heading order) matter for server-rendered pages.
- The Phase 6 run against production needs a different fixture.

The address form's lookup (#105):

- **Pages are answered by Mock Service Worker (MSW),** in `apps/worker/test/page-fixture.ts`, which the integration, browser and VoiceOver tests start. Tests make no requests to the internet, so every address a test looks up is one of the fixture's pages. Their addresses are ordinary `https://` addresses under the reserved `.test` domain, such as `https://pages.test/`, so validation is the production validation, and no name is looked up.
- **Why it works.** `createTestHarness` makes every outbound fetch from the Worker with `globalThis.fetch` in the Node process that started the harness. It is the `outboundService` the harness sets, in `wrangler-dist/cli.js` of Wrangler 4.149.0, and it looks `globalThis.fetch` up on each call. MSW's `setupServer` patches that function, so it answers the Worker's requests in the test's own process. The harness's own requests, such as the integration tests' `server.fetch`, do not go through what MSW patches, so they are not affected. Playwright's request API does, when a browser test calls the Worker from Node, so the browser tests' fixture lets exactly the Worker's own origin through (`allow`, with MSW's `passthrough`).
- **No request goes unplanned.** MSW fails a request that matches no page (`onUnhandledFrame: "error"`). The Worker would only fall back to the address alone, so the fixture also records the address in `unplanned`, and each integration test and each browser test fails when that list is not empty. The browser tests' Worker always starts with the fixture, in `startHaystackWorker`, so the extension's tests are covered too. Their automatic `workerRequests` fixture checks the list after each test, so a failure points to the test that caused it, and the Worker's `close` throws on an unplanned request as a last check. A test shows that a request to `https://example.com/` is recorded and failed.
- **What this relies on, and what it cannot test.** It relies on the harness making the Worker's fetches from Node, which Wrangler does not document. If a Wrangler upgrade makes `workerd` fetch directly, MSW no longer sees the requests, every lookup fails, and the tests fail loudly rather than pass. Because Node makes the request, five things differ from production, and the tests do not rely on them:
  - Node follows redirects itself, so the Worker sees the final response under the first address, and neither redirect handling nor resolving the canonical link against the final address after a redirect is tested.
  - Node keeps reading a body after the Worker has cancelled it, so the cancellation of the rest of the body is not tested: removing `source.cancel()` from `readHead` fails no test. Whether the read stopped is tested by what the Worker took, and by when it answered (see below).
  - A request Node cannot make reaches the Worker as a 500 response rather than an error, so the `network` reason code is not tested.
  - The harness hands a request to the Worker as `http`, even when the test addressed it as `https`.
  - Node adds headers of its own, such as `accept-language`.
- **The fixture before MSW** was a local https server with a self-signed certificate, which the test process trusted through `tls.setDefaultCACertificates`. MSW replaced it (#105), because it needs no certificate, its addresses can be any `.test` host, and it fails a request no test planned for. A test-only `vars` value mapping fetched origins to a fixture, and a service binding to a fixture Worker through `bindingOverrides`, were rejected, because each would put a path that only tests use into production code.
- **Integration tests** (`apps/worker/test/save-address.test.ts`) check the happy path's 303 and every field in its `Location`, with the save form then prefilled from it. They check that values are decoded, matched case-insensitively, taken from the first tag with content, and cut to their caps; that the canonical URL is resolved against a `<base href>`, and kept when it is on another host; that a page in the charset its header names is read correctly; that the page is fetched without tracking parameters; and what the fixture saw: the User-Agent `Haystack (+<origin>)`, `accept: text/html`, and no cookie or authorization even when the user's request had both. A flagged canonical URL is dropped, and a page with long metadata gets a link within the budget, with `og_description` dropped first. Each failure redirects with the address alone and logs its code, and the logs never hold the address or the page's content: a page that never answers (after about 3 seconds), one that stops sending in its head, a network error, 404, 410, 500 and 503, JSON, plain text, XHTML and no content type, no metadata, only blank values, an empty body and a 204, a canonical URL over its cap or not an http(s) link, and a non-UTF-8 charset declared only in `<meta charset>` or `<meta http-equiv>`. An address that is already saved, whatever the case of its host, an address on the Worker's own host, and every rejected address are not fetched, which the fixture's requests show. A signed-out POST (401), a POST from another origin or without an Origin header (403), `GET /save` and `GET /save/address` fetch nothing. The JSON answers for the script are checked too: the save link with the page's fields and with the address alone, the headers, any `Accept` that names `application/json`, a rejected address with its error and whether the value may stay (never for a sensitive one, whose value never appears in the answer), 401 signed out, 403 for the Origin check, and that without JSON the same request still gets the 303 to the same link.
- **Reading stops early.** Three fixture pages never end, as `ReadableStream`s that the test stops, and a Worker that read to the end would never answer, or would answer at the time limit with the address alone. So getting the title back shows where the read stopped.
  - **At `</head>`, and at `<body>` when a page has no `</head>`:** after that point the page trickles on, one small piece every 50 ms, so a read that went on to the byte limit would take far longer than the time limit. The answer comes within half of it, and a meta tag right after that point, in the same chunk, is not read.
  - **At the byte limit:** a head of comments that never ends arrives as fast as the Worker reads it, so only the byte limit can stop the read before the time limit. Comments never reach a handler, so the element budget does not stop it first.
  - **At the element budget:** a head with 150 `og:site_name` tags before its title gives the first tag's value and no title. A head with 200 preload links before its title gives the title, because those links never reach a handler.
  - **Staying fast:** for each path that reaches a handler, a page of nothing but that tag up to the byte limit is looked up, at the fastest of three runs, less than 50 ms slower than a tiny page. The paths are `<meta name="description">`, `<head>`, `<title>x</title>`, an empty `<title>` and `<body>`. With the reader as it is, each measured 0 to 2 ms slower. Before the re-review's fix, `<head>` measured about 130 ms slower and `<title>` about 360 ms, and the meta tag about 90 ms without the budget, so the margin tells them apart with room for a loaded machine. `<body>` measured only about 10 ms slower before the fix, under the margin, so its case holds the path to the margin without showing that fix; removing the stop at `<body>` altogether makes it about 425 ms slower, which it does catch. Counting each chunk of a title's text is a second guard: no test fails without it, because a title's element is counted too. These are timing assertions, so if one proves flaky, the budget test above still shows the budget working.
- **Browser tests** (`apps/worker/e2e/address-form.e2e.ts` and `design.e2e.ts`) take the keyboard path from the saved links page and from a bare `/save` to a filled-in confirmation form. Each point of the form's design has its own named test, numbered as here:
  1. **Without JavaScript,** the form POSTs and follows the 303 to `/save`, unchanged, and a rejected address gets the server's page with the same error as with JavaScript.
  2. **With JavaScript,** the form goes through `fetch` to the same route, which answers JSON.
  3. **Continue is never disabled** (no `disabled`, no `aria-disabled`). Its label changes to "Processing…", and 100 ms later the processing message takes focus, whether Continue or Enter in the field was pressed, with the site's focus ring. A user who moved focus elsewhere first keeps it there (with Playwright's clock).
  4. **A second press with the same address is ignored,** and no second request is sent, whether it is Enter in the field, reached back from the focused message, or a click on Continue. Another test answers the lookup, keeps the browser on the page with a 204 for the save form, and presses Continue and Enter in the field again: no second lookup is sent. Playwright's locators wait for a navigation to finish, which a 204 never does, so that test presses keys through `page.keyboard` and checks which element has focus with `page.evaluate`.
  5. **A press with a changed address** aborts the request in flight and sends a new one, and the aborted request's late answer is ignored. One test clicks Continue; the other moves back from the focused message to the field, changes the address and presses Enter.
  6. **On success,** the browser goes to the same-origin `/save?…` link with its fields. A link on another origin, or to another path, is not followed.
  7. **On a rejected address,** the server's error markup is shown, and the field gets focus, with the error read first in its description, then the hint. A sensitive value is not put back in the field. The page takes the error page's title while the error is shown, and gets its own title back when a new request clears it. A corrected address clears the error, and a page that already shows the server's error gets it replaced, not doubled.
  8. **A timeout after 10 s** (with Playwright's clock), **a network error, 401 (signed out)** and any other answer each show their message, which takes focus, with a sign-in link for 401, and leave the form ready to try again.
  9. **The back-forward cache:** going back from `/save` brings back a form that's ready, and a page restored from the cache while processing is ready again, with its message gone and nothing focused (the test dispatches the `pageshow` event that the browser fires, because Playwright's Chromium does not show whether it used the cache).

  The form shown before sign-in loads no script, and even with the script added to its page, it asks for `GET /save`. In `design.e2e.ts`, each state the script leaves the form in (processing, a rejected address, a timeout, a network error and signed out), on both forms and with the message focused, passes axe in both color schemes and does not scroll horizontally at 320 px, and in forced colors the focused message keeps its 3 px outline. Every one of these tests fails when the behaviour it names is broken in the script or the route.
  - **Clocks are paused.** A test that moves time on installs Playwright's clock with `installPausedClock` (in `e2e/held-lookups.ts`), because `clock.install` alone leaves it running in real time, and a test could race the script's 100 ms.
  - **The review of #105** added tests that each fail without their fix: the region is not live once the script runs; the save link is followed without `URL.parse`; the error goes before the hint in the card and before the form on its own page; a value that must not stay is cleared only while the field still holds it; a failure message does not take focus from a user typing in the field; and a page the server rendered with an error gets its error-free title back after a failure.
  - **The lookups are held in the browser** by `e2e/held-lookups.ts`, with `page.route`, so a test can look at the processing state for as long as it needs, then let a request through, answer it or fail it. The script sends the form with `fetch`, so the page does not navigate while a request is held, and Playwright's locators work as usual. An earlier version cancelled each submission instead, because holding a navigation stops Playwright's locators until it finishes.
  - **The saved links page has two status regions** now, the list's and the address form's, so the delete tests find the list's with `e2e/list-status.ts`.

- **VoiceOver** (`apps/worker/e2e/address-form.voiceover.ts`): the test holds each lookup. After Continue is pressed with VoiceOver on an address without `https://`, the processing message takes focus and should be spoken. Once the request is let through, the server rejects the address, the script moves focus to the field, and VoiceOver should read the field with the error. Then a corrected address is answered with 401, and the signed-out message, which takes focus, should be spoken. The whole spoken log is searched first, as since 42b0867, then `waitForSpoken` (in `e2e/wait-for-spoken.ts`) looks at later phrases. It was written without a local run, so its first CI run is its first check. It assumes that VoiceOver's Space on the focused button submits the form, and that VoiceOver follows focus to the message and to the field, as it did in the investigation's runs. The page's clock is Playwright's, paused, and the test moves it on by the script's 100 ms itself, because on CI a press with Guidepup's `capture: true` waited for VoiceOver longer than the script's 10-second timeout, and the held lookup timed out before the test looked (run 39444075815). Presses now use `capture: "initial"`, and `waitForSpoken` listens after them. The same sequence, with an 11-second wait in real time, passed in plain headed WebKit and in Chromium. The server's error page is still read by VoiceOver in `save-pages.voiceover.ts`, which runs without JavaScript, because with JavaScript the error is shown in place and this test covers it.

The extension's browser tests (#70):

Each Playwright worker process starts the Worker, then builds the extension against the Worker's origin, because the origin is compiled in and the harness picks its port when it starts.

- The extraction function's tests (#72) use a plain browser context, not these fixtures, because they never load the extension. They keep the same rule: they serve the fixture page through a route, abort any other request, and fail if there was one.

  - `signIn` adds the session as a real cookie with `addCookies`, with a `domain` and `path`, so the browser sends it on that first request.
  - The browser resolves no host but the Worker's (`--host-resolver-rules`), so that request cannot reach the network whatever it is. Every request Playwright does see must go to the Worker, the extension or a fixture page, and anything else is aborted and fails the test. - The popup tests rely on `PW_CHROMIUM_ATTACH_TO_OTHER=1`, an environment variable that Playwright does not document. The extension's `playwright.config.ts` sets it.
  - What it does: Playwright's Chromium code (`crBrowser`) attaches to targets of the type `other` and treats them as pages. Without it, Playwright detaches from them.
  - Why the tests need it: the popup's target starts with the type `other`, so without the variable the tests can click the toolbar button but never see the popup. They could not check the refusal message or run axe on it.
  - If a Playwright upgrade removes it, the popup tests fail at once, waiting for the popup, rather than pass without checking anything.
  - Schalk decided to keep it (#70), and to ask Playwright to support it upstream. The request is a comment on [microsoft/playwright#40554](https://github.com/microsoft/playwright/issues/40554#issuecomment-6226217824), which asks for the variable to be documented or replaced by a supported option.
- axe runs in the popup in legacy mode (`setLegacyMode`), because by default it opens a new page to gather its results, and Chromium closes a popup when another page takes focus. The popup has no frames, which are the only thing legacy mode skips.

**Screen reader tests** use Guidepup (`@guidepup/guidepup` and `@guidepup/playwright`), which drives VoiceOver on macOS and records every phrase it speaks. The browser tests check the DOM and the accessibility tree, but not what a screen reader says. The first trial runs showed the difference: VoiceOver read a focused dialog's name and heading, but not its description (#56). Set up in #55:

- The tests live in `apps/worker/e2e` as `*.voiceover.ts`, with their own config (`playwright.voiceover.config.ts`), and run with `vp -C apps/worker run test:voiceover`. `e2e/voiceover-fixtures.ts` combines the browser test fixtures with Guidepup's `voiceOver` fixture through Playwright's `mergeTests`, so each test gets the local Worker, `signIn`, and a running VoiceOver.
- They run one at a time in headed WebKit, Playwright's closest browser to Safari, because there is only one VoiceOver and it cannot read a headless browser. They have one retry, because VoiceOver sometimes fails to start ("Unable to activate application"). That happened to the first test in two of six trial runs, and each time the next test in the same job started VoiceOver normally.
- They are not part of `vp run quality`, because they need macOS with VoiceOver set up for automation, and VoiceOver takes over the machine while they run.
- Checks match the parts of a phrase that matter (for example "heading level 1" and "Saved links"), not whole phrases or a snapshot of the log, because VoiceOver's wording changes between macOS releases.
- Guidepup records one joined entry per command, taken from VoiceOver's last phrase. With `capture: true`, Guidepup keeps looking after a new phrase, waiting about as long as that phrase takes to say between looks, so a long hint can swallow a short phrase that follows it. That is why the status message at first looked as if VoiceOver had never spoken it, when it had (#56). A test that waits for a short phrase uses `waitForSpoken` in `delete-dialog.voiceover.ts`. It uses `capture: "initial"` (Guidepup's default), which looks once and stops, and presses Shift (which does nothing in VoiceOver or on the page) repeatedly, so that Guidepup looks again after each press, until a phrase matches. For anything that VoiceOver moves to, `voiceOver.itemText()` (the text of the item under its cursor) is more reliable than the spoken log.
- The `@guidepup/setup` tool is a dev dependency too, run by the `voiceover:setup` and `voiceover:install` scripts, so the lockfile, the release-age rules and Dependabot cover it. (The Guidepup GitHub Action is archived.) Its optional screen recording depends on `ffmpeg-static`, whose install script downloads an ffmpeg binary without checking it, so `pnpm-workspace.yaml` denies that script, and the setup is never recorded. `voiceover:install` picks the VoiceOver assets that the installed `@guidepup/guidepup` version lists for each macOS version, so the two packages are updated together.
- CI: the VoiceOver workflow runs on GitHub's `macos-26` runner (free, because the repository is public) for pull requests and pushes to `main` that change anything under `apps/` or `packages/`, or the dependencies, and on manual dispatch. The label fixes the macOS major version, but the image still gets 26.x point releases, which can change what VoiceOver says. The job runs `voiceover:setup --ci`, `voiceover:install`, then the tests, and always uploads the Playwright traces and videos, which Playwright keeps only for failed attempts. It is advisory, not a required check.
- Locally the tests are optional. Set up the Mac once:
  1. Run `vp -C apps/worker run voiceover:setup --macos-ignore-tcc-db`. The flag skips the update to the macOS permissions database, which needs System Integrity Protection disabled. Do not disable it: the setup asks for the same permissions by hand instead, as Guidepup's "Manual VoiceOver setup" guide describes. It opens VoiceOver Utility and waits up to five minutes until "Allow VoiceOver to be controlled with AppleScript" is ticked on the General tab.
  2. In System Settings, Privacy & Security, Accessibility, add the terminal or editor that runs the tests to "Allow the applications below to control your computer".
  3. Run `vp -C apps/worker run voiceover:install`, and again after each Guidepup update.

  While the tests run, VoiceOver speaks and takes the keyboard focus, so the Mac cannot be used for anything else.

Tests: the service works without any HTTP request object, the channel is recorded, every candidate is logged including those below the threshold, a deleted bookmark disappears from results and its search answers are removed, the thresholds are read from configuration, batch chunking respects both the 32k state-plus-longest-question budget and the 64k request budget, the limiter holds requests under the per-minute limit, only bookmarks with at least one enrichment are candidates, Held bookmarks are never candidates, each candidate uses its most recent enrichment, an empty collection returns an empty result, a query over the length cap is rejected, a chunk rejected as too large is split and retried, a partial Jev failure shows the successful results with an incomplete notice and is logged as `partial`, a full Jev failure shows an error state rather than an empty list and is logged as `failed`, and the web channel logs `input_mode`.
Acceptance: a real search from the page returns ranked cards, and the logs contain both signals for every candidate.

#### Phase 12: Evaluation harness

Write the labeled query set against the real collection, a replay script that re-ranks logged answers under any threshold without calling Jev, and a comparison script that runs the same labeled queries in pair mode and batched mode.

Outputs: precision and recall at several thresholds for Noul and for Score, the per-pair difference between pair and batched probabilities, the measured tokens per bookmark in batched mode, which sets the real chunk size, the calibrated characters-per-token ratio for the chunker's estimate, p95 search latency against collection size, which sets the shortlisting trigger (Q11), and a comparison of `match_text` derivations with and without `technologies`, `topics`, and `problems_solved`. Pair-mode evaluation runs must stay under the 1,200 requests per minute limit.
Acceptance: Schalk can choose a default signal, a default threshold, and a request mode based on data, and can decide whether search keeps asking both questions. Each choice is applied by changing a Flagship flag, without a deploy.

#### Phase 13: Voice

Add the microphone button and browser speech recognition behind feature detection, as described under "Search page."

Tests: Playwright replaces the speech recognition constructor with a stub through an init script, because tests cannot use a real microphone. The button is not rendered when the API is missing; the button's accessible name and listening state are announced; a stubbed result fills the input without submitting it; each stubbed error (permission denied, no speech, network) ends listening and shows its message; and the run logs `web-speech` as `input_mode` when the query came from speech and `typed` when the user typed it or replaced the transcript.
Acceptance: in Chrome, a spoken query fills the input and searches after confirmation, and `input_mode` is logged on each run.

#### Phase 14: Search release

Deploy Milestone 3 and run the Playwright suite against production. Once Q6 is resolved, move to the custom domain: update the Google OAuth redirect URIs and rebuild the extension with the new origin.

Acceptance: the end-to-end flow works in production: save from the extension, enrichment, then search.

### Milestone 4: Agent access

Goal: agents can search the user's bookmarks, first from the browser through WebMCP, then from any MCP client. Search only.

#### Phase 15: WebMCP search tool

Define the `search_bookmarks` tool's input and result schemas in `packages/schemas`. Register the tool on the search page when the WebMCP API is available, calling `/api/search` with the page's session and recording `channel` as `webmcp`. Q9 must be resolved first.

Tests: the tool is not registered when the API is unavailable, the tool's results match the web search for the same query, results contain only title, description, URL, and kind, Held bookmarks never appear, and the run is logged with the `webmcp` channel. Use the browser's WebMCP testing interface where available, otherwise test the tool's execute function directly.
Acceptance: an in-browser agent can find a bookmark by describing it.

#### Phase 16: MCP authorization

Implement authorization for MCP clients as decided in Q8, with Google sign-in as the identity step and the `ALLOWED_EMAILS` check applied to every request. Q8 must be resolved first.

Tests: follow the authorization section of the 2026-07-28 specification as the checklist, including the issuer and client validation it requires, and additionally: a request without a valid token is rejected, a token for a user removed from `ALLOWED_EMAILS` is rejected, and a revoked token is rejected.
Acceptance: an MCP client completes authorization through Google sign-in and receives a token scoped to one Haystack user.

#### Phase 17: Remote MCP search server

Implement `/mcp` on the stateless 2026-07-28 specification with the search tool only, calling `searchBookmarks` with the `mcp` channel, and add a per-user rate limit. Use the official TypeScript SDK if its current release supports this specification revision on Workers; otherwise implement the small required surface directly.

Tests: required discovery and tool listing work without any prior request, a tool call works as a single self-contained request, a request for any tool other than search is rejected, results match the web search for the same query, the rate limit applies per user, and the run is logged with the `mcp` channel.
Acceptance: Claude and at least one other MCP client can search Haystack by describing a bookmark.

#### Phase 18: Agent access release

Deploy Milestone 4, document how to connect an MCP client, and review the search logs by channel after a week of use.
